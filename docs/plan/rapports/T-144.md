# T-144 — Invite du composteur

Origine : relecture réseau R-6 de T-141 (`docs/plan/rapports/T-141.md`), et R-3 pour `stationTypes.*.prop`. Critères :
entrée T-144 de `docs/plan/BACKLOG.md`. Procédure en jeu : `docs/tests/metiers.md` 5-7 ; README de `vava_crafting`,
test 15 et « À vérifier en jeu (1.7.0) ».

## Le problème

Le type `composteur` est déclaré au registre `vava_crafting:stations` par `vava_farming`, côté serveur seulement. Le
client cherchait le type d'une station dans `cfg.stationTypes` de sa config (`client/props.lua`, `props.type`) : absent,
`interact.refreshPrompt` cachait l'invite. La station était dessinée (son modèle part déjà avec son dessin), mais sans
invite ; `E` pouvait l'ouvrir à l'aveugle (le menu ne dépendait que de la station la plus proche).

## Ce qui change (`vava_crafting` 1.6.0 → 1.7.0)

- **Dessin d'une station** (`shared/stationzone.lua`) : `stationzone.drawing` ajoute `typeLabel` (nom du type) et
  `capacity` (réserve de combustible du type, absente sans combustible), pris du type résolu par le serveur.
  `readDrawing` exige `typeLabel` (chaîne de 1 à 128 octets, la borne des noms) et n'admet `capacity` qu'entière, de 1 à
  `VavaCrafting.FUEL_CAPACITY_MAX` ; sinon la station est ignorée, sans erreur. `sameDrawing` compare les deux champs :
  un type renommé ou une réserve changée replace la station (l'invite suit).
- **Borne** : `FUEL_CAPACITY_MAX = 10000` dans `shared/constants.lua` (règle R6 de T-132 : borne de protection du
  client, jamais dans `config_client.lua`) ; le serveur applique la même au schéma du registre des types
  (`server/catalog.lua`, `capacity.max`), à la place du 10000 écrit en dur.
- **Client** : `interact.refreshPrompt` lit `station.typeLabel` et `station.capacity` dans le dessin ; `props.type` et
  `modelFor` retirés (le modèle du dessin est déjà celui de la station, sinon de son type) ; l'animation d'un geste est
  celle que nomme le serveur dans sa réponse (`result.anim`, déjà envoyée par `crafting.begin` et `repair.begin`), et
  seulement si c'est une chaîne. Le client ne lit plus rien des types.
- **Config** : `stationTypes` quitte `config_client.lua` pour `config.lua` (entier : le client n'en lit plus aucune
  feuille, T4 l'exige), valeurs inchangées, avec un `-- PLACEHOLDER (modèle)` par type. `anims` reste au client.
  `catalog.define` refuse le module avec un message clair si aucune table `stationTypes` n'existe (`config.lua` d'avant
  1.7.0 gardé par l'installeur avec le `config_client.lua` neuf) au lieu d'une erreur Lua.
- Le serveur reste juge : rien de nouveau n'est décidé côté client ; l'invite n'affiche que ce que le serveur publie
  dans la zone de la station ; le menu est toujours demandé par le RPC `open`, qui revérifie distance, accès et
  occupation.

**Aucun RPC ni évènement ajouté ou modifié.** Le contrat de l'état de zone `def` change (deux champs) : `docs/api.md`
et le README (« Réseau ») sont à jour.

## Choix

- Piste du backlog suivie : le nom du type et la réserve partent avec le dessin, plutôt qu'un envoi des types au client
  (qui aurait servi des compétences et des objets de combustible à tout le monde, et rien pour un type ajouté plus tard).
- `typeLabel` exigé (le serveur le pose toujours ; le registre impose un nom de 1 à 48 octets) : un dessin sans nom de
  type est mal formé. Serveur et client sont la même ressource, aucun mélange de versions à prévoir.
- Point 4 de la demande (retirer `stationTypes.*.prop` du client) : fait, et au-delà, toute la table, puisque plus aucun
  fichier client ne la lit. T2 (le client ne lit que sa part) et T4 (le client ne reçoit que ce qu'il lit) passent sans
  exception ni changement de `config_split_spec`.
- `vava_farming` n'est pas touché (T-136 y travaille).

## Essais

- `tests/spec/crafting_prompt_client_spec.lua` (nouveau) : `client/nui.lua`, `client/props.lua` et
  `client/interact.lua` chargés sur la **seule vue client** (`helper.loadClientView`), doublures du core et des natives.
  Le dessin du composteur est construit comme le serveur le publie, depuis `config.composter` de `vava_farming`. Vérifie :
  le client ne connaît aucun type ; au composteur du champ, l'invite `{ key, label = 'Composteur du champ',
  typeLabel = 'Composteur', busy = false }`, sans combustible, et le modèle du type ; à la forge, la réserve reçue
  (`{ stock = 0, capacity = 20 }`) et suivie quand le combustible change ; `E` demande le menu au serveur (`open`,
  identifiant du composteur), l'affiche avec le focus et cache l'invite ; le geste joue l'animation nommée par le serveur,
  rien sur une réponse informe.
- `tests/spec/crafting_stationzone_spec.lua` : dessin avec nom du type et réserve (et sans réserve pour un type sans
  combustible) ; lecture : `typeLabel` absent, vide, non chaîne, trop long refusés ; `capacity` 0, négative, décimale,
  NaN, infinie, texte, au-delà de la borne refusées, 1, la borne et 20.0 admises ; types livrés dans les bornes ; carnet
  qui replace une station dont le type est renommé ou la réserve changée.
- `tests/spec/crafting_stations_share_spec.lua` : dessin d'essai complété de `typeLabel` (contrat).
- Mutation jouée : invite de nouveau conditionnée à `cfg.stationTypes` → trois essais du nouveau fichier échouent.
- Comparaison clé par clé de la config complète (constantes, `config_client.lua`, `config.lua`) avant et après, par un
  script hors dépôt : **0 différence** ; vue client : `stationTypes` absent.

côté client (menu, recettes, droit, combustible au serveur ; `capacity` d'affichage seulement) ; `typeLabel` borné à
