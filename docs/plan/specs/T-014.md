## 1. But joueur

Quand on arrive à la place du marché, à la mine du Val ou au champ communal, ce qui s'y passe (charges des filons,
cultures, forge occupée, voix qui porte sur la tribune) est déjà là ; ce qui se passe à l'autre bout du royaume ne coûte
rien à notre connexion. Le Conseil peut créer et déplacer des lieux en jeu (Atelier) sans que chaque retouche parte chez
tout le monde.

Piliers du lore : « Ressources exploitées avec mesure » (la vitalité des zones et les charges des nœuds restent vues de
ceux qui récoltent, sans coût pour les autres) et « Les saisons célébrées, les récoltes rassemblent » (beaucoup de
joueurs au même endroit : seul l'état local leur est envoyé).

## 2. Périmètre

Dedans :
- **`core.zones`** (API serveur v1, additive) : un module déclare des zones (centre, rayon, marge), tient leur **état**
  (paires clé → valeur) dans le core, le change par petites différences, les déplace, les retire.
- **Abonnements calculés par le serveur** : à chaque passage (1 s), le core lit une fois la position de chaque joueur
  présent, cherche dans une grille les zones proches, abonne (instantané + numéro de révision) ou désabonne (avec une
  marge contre les allers-retours). Le client ne demande jamais d'entrer dans une zone.
- **Révisions** : chaque envoi d'état porte la révision de la zone ; le client applique `révision + 1`, ignore l'ancien,
  et redemande l'instantané (`core:zones:resync`, seul RPC ajouté) en cas de trou.
- **Côté client** : réception, répliques des zones abonnées, règles de révision, notification du module propriétaire
  (`core.zones.watch`), nettoyage à la sélection, au déchargement et à l'arrêt d'un module.
- **`core.net`** : cache des positions de 50 ms, plafond global du latent, liste des joueurs sautés, `sendPacked` et
  `sendNearPacked`.
- **`/vava_reseau zones [n°]`** : zones déclarées, abonnements, durée du dernier passage ; zones suivies par un joueur.
- **`vava_voice` 1.3.0** : zones de voix par abonnement ; fin de l'envoi à tous ; exceptions d'audit retirées.

Hors périmètre :
- Bascule de la récolte, de l'agriculture et de l'artisanat (T-015, T-016, T-017) : ils gardent GlobalState jusqu'à leur
  tâche ; le § 13 dit ce que chacune fera.
- Stockage et versions des définitions de l'Atelier (T-101), catalogues de gestes, effets, sorts (envoyés une fois avec
  un numéro de version, pas par zone).
- Formes autres que le cercle (polygone, couloir) : un module donne le cercle qui englobe sa forme (décision 2).
- Zones dont l'état ne serait vu que de certains joueurs (accès privé, essai de l'Atelier réservé à son auteur) : ce
  qui est privé part par `core.net.send` au seul intéressé.
- Bascule des autres envois des modules sur `core.net` (inventaire, magie, chat…) : tâche déjà relevée par T-013
  (rapport § Hors périmètre), qui se servira de `sendPacked`.
- Page « Réseau » de la Chancellerie (T-049).

## 5. Données

Aucune table SQL, aucune migration, aucun champ de personnage, aucune métadonnée d'objet. Tout vit en mémoire du
serveur ; chaque module redéclare ses zones à son démarrage (sa base ou sa config fait foi).

Mémoire bornée (ordre de grandeur) :
- par zone : ~400 o de structure + son état (≤ 32 Ko, ≤ 8 Mo pour toutes) + un drapeau par abonné ;
- par joueur : un ensemble de numéros de zones (≤ 256) ;
- grille : une entrée par case couverte (cercle d'intérêt ≤ 1 000 m de rayon : ≤ 81 cases de 256 m par zone) ;
- **aucune révision passée n'est gardée** : un trou se répare par un instantané complet ;
- client : une réplique par zone suivie (≤ 256) et au plus 32 différences en attente par zone.

### Forme d'une zone (serveur)

```lua
-- area : centre au sol, rayon, marge ; z accepté et ignoré (la distance est horizontale, décision 2)
{ x = -320.0, y = -880.0, z = 31.0, radius = 120.0, margin = 100.0, bucket = nil }
```

- **Intérieur d'intérêt** (abonnement) : distance horizontale au centre ≤ `radius + margin`.
- **Sortie** (désabonnement) : distance horizontale > `radius + margin + exitMargin`.
- `bucket` : entier ≥ 0, seuls les joueurs de ce routing bucket s'abonnent ; absent : tous les buckets (même règle que
  `sendNear`, décision 7 de T-013).

### État d'une zone

Table à **clés chaînes** (motif d'identifiant `^[%w_%-%.:]+$`, 48 octets au plus) → valeurs sérialisables (nombre,
chaîne, booléen, table sans fonction ni cycle, profondeur ≤ 32 : règles de `netsize`). Jamais de clé entière (une table
à clés 1..n deviendrait une liste, une table mixte perdrait ses clés : `docs/api.md` § Copies). Exemples :

```lua
{ zone = { band = 'normal', scarred = false }, ['n:chene_1'] = 3, ['n:chene_2'] = 0 }   -- récolte (T-015)
{ s1 = { crop = 'ble', stage = 2, state = 'ok' }, s2 = { crop = '', stage = 0, state = '' } } -- parcelle (T-016)
{ zone = { id = 12, label = 'Tribune', x = 1.0, y = 2.0, z = 30.0, radius = 10.0, height = 6.0, multiplier = 2.0 } } -- voix
```

Révision : entier ≥ 1, `1` à la déclaration, `+1` à chaque différence envoyée ou état remplacé. Numéro de zone
(`handle`) : entier ≥ 1 donné par le core à la déclaration, jamais redonné pendant la vie du core (un retrait puis une
redéclaration donnent un nouveau numéro) ; au-delà de `vAvA.RPC_MAX_ID`, `define` rend `full`.

## 6. Réseau

### 6.1 API serveur `core.zones` (modules)

Toutes les fonctions sont gardées (module actif, comme le reste de l'API), ne lèvent jamais d'erreur et ne touchent que
les zones du module appelant : l'identifiant local `id` devient le nom `<ressource>:<id>`.

| Fonction | Retour |
|---|---|
| `define(id, area, state?)` | `true, handle` ou `false, code` |
| `move(id, area)` | `true` ou `false, code` — centre, rayon, marge, bucket changés ; état et abonnés gardés, réévalués au passage suivant |
| `set(id, changes, removed?)` | `true` ou `false, code` — `changes` : clé → nouvelle valeur ; `removed` : liste de clés retirées ; envoyé aux abonnés en fin de tour, regroupé avec les autres changements de la zone faits dans le même tour |
| `replace(id, state)` | `true` ou `false, code` — tout l'état remplacé, instantané aux abonnés (rechargement, publication de l'Atelier) |
| `remove(id)` | `true` ou `false, code` — les abonnés reçoivent la sortie |
| `subscribers(id)` | liste des joueurs abonnés (copie), ou `nil, code` — pour cibler un son, un effet, un message de lieu |
| `info(id)` | `{ handle, revision, subscribers, keys, bytes }` ou `nil, code` |
| `list()` | liste des identifiants locaux du module, triée |

- `id` : identifiant (`str.isIdentifier`) de 48 octets au plus ; `invalid_id` sinon ; déjà pris par ce module : `exists`
  ; inconnu : `unknown_zone`.
- `area` : table à clés connues (`x`, `y`, `z`, `radius`, `margin`, `bucket`), nombres finis, `|x|, |y| ≤ coordLimit`,
  `0 < radius ≤ maxRadius`, `0 ≤ margin ≤ maxMargin` (défaut `defaultMargin`), `bucket` entier ≥ 0 ; sinon
  `invalid_area`.
- `state` / `changes` : table à clés chaînes valides (`invalid_key`), valeurs sérialisables (`invalid_value` : fonction,
  cycle, profondeur > 32, `nil` impossible dans une table), chacune ≤ `maxValueBytes` (`too_large`) ; au plus
  `maxChanges` clés par appel et `maxKeys` dans l'état (`too_many_keys`) ; état ≤ `maxStateBytes` (`too_large`) ; somme
  des états ≤ `maxTotalStateBytes`, nombre de zones ≤ `maxZones` et `maxZonesPerOwner` (`full`). `removed` : liste pure
  de clés valides. Rien n'est appliqué si un seul élément est refusé (tout ou rien).
- Une valeur **scalaire** égale à la valeur actuelle n'est pas marquée changée (rien ne part) ; une table est toujours
  considérée changée (le module compare lui-même s'il le veut, comme le font déjà la récolte et l'artisanat).
- Coût de la traversée d'export : seules les valeurs changées la traversent (une copie, quelques dizaines d'octets
  d'ordinaire) ; l'instantané, lui, est fait par le core à partir de sa copie : il ne traverse jamais l'export.

Exemple (forme que prendra T-015) :

```lua
core.zones.define('foret_brume', { x = -320.0, y = -880.0, radius = 140.0, margin = 100.0 },
    { zone = { band = 'normal', scarred = false }, ['n:chene_1'] = 3 })
-- une récolte : un seul envoi aux abonnés, en fin de tour, pour les deux clés
core.zones.set('foret_brume', { ['n:chene_1'] = 2 })
core.zones.set('foret_brume', { zone = { band = 'reduced', scarred = false } })
```

### 6.2 Évènements serveur → client du core

Tous passent par `vAvA.net` (comptés, jamais `-1`) ; la colonne « compté sous » donne la clé de `/vava_reseau`.

| Évènement | Valeurs | Cible (qui, pourquoi) | Taille | Envoi | Compté sous |
|---|---|---|---|---|---|
| `vAvA:zone:state` | `handle, name, revision, state` | les joueurs qui **entrent** dans la zone pendant ce passage (position serveur dans le cercle d'intérêt), groupés en une liste : une seule sérialisation ; le joueur qui demande un `resync` ; tous les abonnés à jour sur `replace` ou différence trop grosse | 40 o + état (voix ~150 o, parcelle ~500 o, zone de récolte ~400 o ; ≤ 32 Ko) | `auto` : fiable ≤ 8 Ko, latent au-delà | module de la zone, `vAvA:zone:state` |
| `vAvA:zone:pending` | `handle, revision, delayMs` | le même joueur, **juste avant** un instantané parti en latent (préavis : il garde les différences qui arriveront avant) | ~30 o | fiable | module de la zone, `vAvA:zone:pending` |
| `vAvA:zone:diff` | `handle, revision, set, removed` | les abonnés **à jour** de la zone (pas ceux dont l'instantané attend) | 30 à 80 o d'ordinaire ; ≤ 8 Ko | **toujours fiable** (`never`) : jamais sautée | module de la zone, `vAvA:zone:diff` |
| `vAvA:zone:leave` | `handles` (liste) | le joueur qui sort d'une ou plusieurs zones pendant ce passage (un seul message pour toutes) ; tous les abonnés d'une zone retirée | 20 o + 3 o par zone | fiable | `vAvA_core`, `vAvA:zone:leave` |

- `name` = `<ressource>:<id>` (le client en tire le module propriétaire) ; `set` : table clé → valeur ou `nil` ;
  `removed` : liste de clés ou `nil`.
- Ordre garanti par construction : un instantané fiable précède les différences suivantes (même canal fiable) ; un
  instantané latent est annoncé par `vAvA:zone:pending` (fiable, envoyé avant), et le client garde les différences
  plus récentes jusqu'à son arrivée (§ 8.2).
- **Aucun envoi à tous**, aucun GlobalState, aucun state bag. Un joueur sans zone à portée ne reçoit rien.

Estimation (récolte, T-015, 64 joueurs dont 15 à la mine) : une récolte = une différence d'environ 50 o vers les
abonnés de la zone (15 joueurs) ≈ 0,75 Ko, contre ~140 o × 64 = 9 Ko aujourd'hui par GlobalState.

### 6.3 Passage (entrées et sorties)

Toutes les `passMs` (chaîne de `SetTimeout`, pas de boucle `Wait`), et pour un seul joueur à l'apparition confirmée
(`refreshPlayer`) :

1. Envoyer les différences en attente de toutes les zones (§ 6.4) : un instantané fait ensuite est toujours au moins
   aussi récent.
2. Pour chaque personnage **présent** (`characters.forEachActive`, `sync.isCurrent`) : position par
   `net.positionOf(src)` (une lecture, gardée 50 ms) et `GetPlayerRoutingBucket(src)`, lus une fois.
   - Pas de ped (position inconnue) : le joueur est sauté pour ce passage, ses abonnements restent.
   - **Sorties** : chaque zone suivie dont il est sorti (distance > rayon + marge + `exitMargin`), retirée, ou dont le
     bucket ne correspond plus → abonnement retiré, numéro ajouté à sa liste de sortie.
   - **Entrées** (seulement si `character.spawned`) : zones de la case de grille du joueur, non suivies, dans le cercle
     d'intérêt, bucket compatible → abonnement « en attente d'instantané » ; tant que `maxSubscriptionsPerPlayer`
     n'est pas atteint.
   - Les zones « en attente » du joueur (nouvelles, ou instantané refusé au passage précédent) sont classées de la
     plus proche à la plus lointaine et retenues jusqu'à `snapshotBudgetBytes` (taille estimée de leur état ; la
     première toujours retenue).
3. Une liste de sortie non vide → un `vAvA:zone:leave` au joueur.
4. Pour chaque zone qui a des joueurs retenus : **une** préparation de l'instantané (`net.prepare`), livrée à la liste
   (`net.deliverList`, préavis `vAvA:zone:pending` pour chaque cible si latent). Les joueurs servis passent « à jour » ;
   les sautés (`saturated`, plafond par joueur ou global) restent « en attente » et sont repris au passage suivant.
5. Durée du passage mesurée (`os.clock`) et gardée pour `/vava_reseau zones`.

Coût attendu (64 joueurs, 2 048 zones) : 128 lectures de natives, une case de grille par joueur (une dizaine de zones
candidates), ses abonnements (une dizaine) : moins de 0,2 ms par passage, une fois par seconde (à vérifier en jeu).

Un personnage **apparu** puis renvoyé à une apparition (mort, `spawn` du serveur : `spawned` repasse à faux) garde ses
abonnements : seules les nouvelles entrées attendent l'apparition confirmée ; rien n'est renvoyé pour rien.

### 6.4 Différences et révisions (serveur)

- `set` applique aussitôt les valeurs à l'état du core et les note dans les changements en attente de la zone (une clé
  changée puis retirée dans le même tour n'apparaît que dans `removed`, et l'inverse) ; le premier changement d'un tour
  programme l'envoi (`SetTimeout(0)`, une seule minuterie pour toutes les zones, comme `sync.lua`).
- À l'envoi (fin de tour, début de passage, avant un `resync`) : révision `+1` ; si la différence regroupée dépasse
  `maxDiffBytes` (taille estimée), l'**instantané** part à sa place vers les abonnés à jour (`auto`, avec préavis s'il
  est latent ; les sautés repassent « en attente ») ; sinon `vAvA:zone:diff` en fiable aux abonnés à jour. Aucun
  abonné à jour : la révision avance quand même, rien ne part.
- `replace` : changements en attente oubliés, état remplacé, révision `+1`, instantané aux abonnés à jour.
- `remove` : `vAvA:zone:leave { handle }` à tous les abonnés (à jour et en attente), zone retirée de la grille et de la
  mémoire.

### 6.5 `core.net` (ajouts)

- **Cache des positions** : `pedPosition` garde une position `near.positionCacheMs` (50 ms) au lieu d'une milliseconde
  (cache vidé quand `GetGameTimer() − instant du remplissage ≥ 50`). `net.positionOf` est celle que lit le passage.
- **Plafond global** : à chaque envoi latent (une fois par envoi, pas par cible), le core calcule le volume en route de
  tous les joueurs (`Σ max(0, drainAt − now) × débit / 1000`, joueurs ayant une échéance seulement) puis l'augmente de
  chaque cible acceptée ; une cible qui ferait dépasser `maxTotalInFlightBytes` est refusée comme une cible saturée
  (`saturated`, ou sautée dans une liste), avec une erreur en console distincte : « plafond global du latent atteint
  (N octets en route) ». `net.wouldSaturate` tient compte des deux plafonds.
- **Joueurs sautés** : `send`, `sendWith`, `sendNear`, `sendNearWith` (et `dispatch`, `dispatchNear`, `deliver` en
  interne) rendent en 5e valeur la **liste des joueurs sautés** (latent refusé) quand la cible est une liste ou un
  rayon, `nil` s'il n'y en a aucun. Nouvelle fonction interne `net.deliverList(owner, label, list, options, packet,
  notice)` → `true, servis, sautés, octets, latent` (deux listes neuves) pour le service des zones.
- **`sendPacked(options, target, event, payload)` et `sendNearPacked(options, coords, radius, event, payload)`**
  (surface des modules) : `payload` = chaîne produite par `msgpack.pack_args(...)` **dans le module** ; mêmes contrôles
  que `send` / `sendNear` (cible, préfixe, options, rayon, saturation, plafonds) ; `#payload + #event ≤ maxBytes`
  (`too_large`), chaîne non vide (`invalid_args`) ; le core l'envoie telle quelle (`TriggerClientEventInternal` /
  `TriggerLatentClientEventInternal`). Mode estimation (fonctions du runtime absentes, ou repli après une erreur) :
  `false, 'unsupported'`, rien n'est envoyé ; le module renvoie alors par `send`. Un envoi interne qui échoue pour un
  paquet sans valeurs ne peut pas être rejoué : erreur en console, cible comptée comme sautée.

```lua
-- dans le bridge d'un module (forme recommandée)
local function sendTo(target, event, ...)
    if type(msgpack) == 'table' and type(msgpack.pack_args) == 'function' then
        local ok, code = core.net.sendPacked(nil, target, event, msgpack.pack_args(...))
        if ok or code ~= 'unsupported' then return ok, code end
    end
    return core.net.send(target, event, ...)
end
```

## 8. Client

### 8.1 Boucles

**Aucune boucle**, aucun thread permanent. Quatre gestionnaires d'évènement, une minuterie (`SetTimeout`) par zone
dont l'instantané est attendu ou redemandé, un `CreateThread` par demande de `resync` (au plus une à la fois par zone).

### 8.2 Répliques et révisions (`shared/lib/zonereplica.lua`, pur)

Une réplique par numéro de zone : `revision` (nil avant le premier instantané), `state`, `buffer` (≤ `maxBuffered`
différences, rangées par révision), `awaiting` (instantané attendu), `overflow`.

| Reçu | Règle | Résultat |
|---|---|---|
| instantané `r` | si `revision` connue et `r < revision` : ignoré ; sinon état remplacé, `revision = r`, `awaiting = false`, puis différences gardées appliquées dans l'ordre (≤ `r` jetées, `r + 1` appliquée…) | `'ready'` (le module reçoit `enter` avec l'état final) ; s'il reste un trou ou si des différences ont débordé : `'resync'` (et `awaiting`) |
| différence `r`, réplique à jour | `r ≤ revision` : ignorée ; `r = revision + 1` : appliquée ; `r > revision + 1` : gardée, `awaiting = true` | `'ignored'`, `'applied'` (le module reçoit `change`), `'resync'` |
| différence, instantané attendu | `r ≤ revision` (si connue) : ignorée ; sinon gardée ; tampon plein : `overflow = true`, la nouvelle n'est pas gardée | `'ignored'`, `'buffered'` |
| préavis `r` | `revision` inconnue ou `r > revision` : `awaiting = true` | `'awaiting'` |
| sortie | réplique retirée | `'left'` (le module reçoit `leave` s'il avait reçu `enter`) |

### 8.3 Service client (`client/core/zones.lua`)

- **Évènements** (valeurs vérifiées, sinon ignorées) : `handle` entier 1 à `RPC_MAX_ID`, `name` chaîne ≤ 113 octets de
  forme `<ressource>:<id>`, révision entier ≥ 1, `state` table, `set` table ou nil, `removed` table ou nil, `delayMs`
  entier ≥ 0, `handles` liste d'entiers (≤ 256).
- **Préavis** : réplique créée si besoin (propriétaire inconnu jusqu'à l'instantané), minuterie `min(delayMs +
  awaitMarginMs, maxAwaitMs)` ; à son échéance, toujours attendu (même génération) → `resync`.
- **`resync`** : `rpc.call('core:zones:resync', handle)` dans un `CreateThread` ; `false, 'not_subscribed'` → réplique
  retirée (`leave` au module s'il l'avait) ; échec de transport (`rate_limited`, `timeout`…) → nouvel essai après
  `resyncRetryMs`, doublé à chaque échec jusqu'à `resyncMaxRetryMs`, tant que la réplique attend. Une ligne `debug` en
  F8 : `[vAvA][zones] instantané redemandé : <nom> (attendu n, reçu m)`.
- **Notifications** au module propriétaire, par le gestionnaire qu'il a donné à `core.zones.watch` (appel sous `pcall`,
  erreur écrite en console avec le nom du module, une par minute) : `('enter', id, state)`, `('change', id, set,
  removed)` (`set` et `removed` jamais nil : tables vides au besoin), `('leave', id)` ; `id` = identifiant local (sans
  le préfixe). Un module qui appelle `watch` reçoit aussitôt un `enter` pour chacune de ses zones déjà à jour (module
  client redémarré, ou instantané arrivé avant son `watch`).
- **Nettoyage** : hooks client `core:character:unloaded` et `core:character:selection` → toutes les répliques retirées,
  `leave` à chaque module pour ses zones notifiées ; arrêt d'une ressource (`client/init.lua`) → ses répliques et son
  gestionnaire oubliés, sans notification.

### 8.4 API client `core.zones`

| Fonction | Retour |
|---|---|
| `watch(handler)` | `true` ou `false, err` — un gestionnaire par ressource (un second appel remplace le premier) |
| `get(id)` | copie de l'état de la zone du module et sa révision (`state, revision`), ou `nil` |
| `list()` | identifiants locaux des zones du module à jour, triés |

Seules les zones **du module appelant** sont visibles (un module ne lit pas les zones d'un autre).

### 8.5 Ce qui est affiché

Rien par le core. Le module affiche ce que sa réplique contient (props, effets, menus) ; quand il n'est pas abonné, il
n'en sait rien et garde ses valeurs par défaut (déjà le cas avec GlobalState non publié).

## 12. Risques

| Risque | Fermeture |
|---|---|
| Un client s'abonne à une zone lointaine ou interdite | aucun RPC d'abonnement : le serveur décide seul à partir de ses positions ; `resync` ne sert que les zones déjà suivies (`not_subscribed` sinon) |
| Client qui ment sur sa position | positions lues côté serveur ; personnages apparus et toujours ceux de leur joueur |
| Spam de `resync` | RPC limité (4, puis 1 toutes les 2 s) + limite globale du joueur ; il ne reçoit que des zones qu'il suit déjà, à lui seul (≤ 32 Ko chacune) |
| Différence perdue ou dans le désordre | différences toujours fiables ; instantané latent annoncé par préavis fiable ; révision attendue + 1, sinon instantané redemandé ; tampon borné |
| Instantané refusé (saturation par joueur ou globale) | abonnement « en attente » : ni différence ni état partiel, instantané au passage suivant à la dernière révision |
| Pic à l'arrivée dans un lieu dense (téléportation, connexion au marché) | budget de 32 Ko d'instantanés par joueur et par passage, les plus proches d'abord ; latent au-delà de 8 Ko ; plafond global de 4 Mo en route |
| Mémoire gonflée par un module | 2 048 zones, 1 024 par module, 256 clés et 32 Ko par zone, 8 Mo pour tous les états, 256 zones suivies par joueur ; aucune révision passée gardée ; tout oublié à l'arrêt du module et au départ du joueur |
| Aller-retour en bordure de zone | hystérésis de 25 m |
| Joueur d'une autre instance au même endroit | option `bucket` de la zone (comme `sendNear`) ; par défaut tous les buckets (décision 7 de T-013) |
| Envoi à tous déguisé | aucune fonction du service ne prend `-1` ; tout passe par `vAvA.net` qui le refuse ; exceptions de la voix retirées, l'audit le vérifie |
| Module qui pousse un état énorme par différences | `maxValueBytes`, `maxChanges`, `maxStateBytes` ; différence regroupée > 8 Ko → instantané (latent au-delà de 8 Ko) |
| Double sérialisation | état tenu par le core (instantané fait sur place, une seule sérialisation pour tous les entrants) ; `sendPacked` pour les envois directs |
| Numéro de joueur redonné | `purgePlayer` au départ et au déchargement ; `isCurrent` au passage |
| Coût serveur du passage | grille, une lecture de position par joueur et par passage, 1 passage/s ; durée affichée par `/vava_reseau zones` |

## 13. Plan de migration

Chaque module bascule **en entier dans sa propre tâche** (serveur et client sont dans la même ressource et changent
ensemble) : pas de double publication, pas de couche de compatibilité. Tant qu'un module n'a pas basculé, il garde
GlobalState (l'audit continue de l'avertir). Chaque bascule déclare `coreVersion = '0.11.0'`, et à son `setup` efface
une fois les anciennes clés GlobalState encore présentes (`if GlobalState[key] ~= nil then GlobalState[key] = nil end`
— un seul envoi, utile seulement si le serveur n'a pas redémarré depuis l'ancienne version), puis n'y écrit plus.

### 13.2 T-015 — Récolte

- Une zone du core par zone de récolte : nom local = id de la zone ; centre = centre de la zone ; rayon = plus grande
  distance horizontale entre ce centre et ses nœuds, au moins `zone.radius` ; marge = `streaming.radius` + 20 m
  (nouvelle clé `streaming.subscribeSlack = 20.0`).
- État : `zone` → `{ band, scarred }` (**sans `vitality`**, comme le demande T-015) et `n:<nœud>` → charges.
  `zones.publish` → `core.zones.set(id, { zone = … })` ; `nodes.publish` → `core.zones.set(zoneId, { ['n:' .. id] =
  charges })` : une récolte (zone et nœud dans le même tour) = une seule différence.
- Client : `props.lua` perd `AddStateBagChangeHandler` et les lectures de GlobalState ; `zoneStates` et `nodeCharges`
  remplis par `core.zones.watch` (`enter`, `change`), vidés pour la zone sur `leave` (valeurs par défaut) ; la boucle de
  props ne mesure plus que les groupes des zones suivies.

### 13.3 T-016 — Agriculture

- Une zone du core par parcelle : centre de la parcelle ; rayon = demi-diagonale de la grille d'emplacements (et du
  grenier, des puits rattachés s'ils sont plus loin) ; marge = `streaming.radius` + 20 m.
- État : `s<n°>` → `{ crop, stage, state }` (chaînes vides pour un emplacement libre). `slots.publish` garde la
  signature **par emplacement** et n'envoie que les emplacements changés (`set` de quelques clés, ~40 o) ; l'état
  complet ne part qu'à l'entrée.
- Puits et composteur : statiques (config) jusqu'à T-103, qui les fera entrer dans l'état de la parcelle.

### 13.4 T-017 — Artisanat

- Une zone du core par station (config et `addStation` des autres modules) : centre = station, rayon 2 m, marge =
  `streaming.radius` + 20 m.
- État : `def` → ce qu'il faut pour la dessiner (`type`, `label`, `x`, `y`, `z`, `heading`, `quality`) et `s` → `{ fuel,
  busy }`. La clé globale `vava_crafting:stations` disparaît : le client ne connaît que les stations proches ;
  `stations.adopt` déclare la zone, le retrait d'une station la retire.
- Les sons de forge et autres envois liés à une station peuvent viser `core.zones.subscribers(id)` ou `sendNear`.

### 13.5 Atelier (T-101, T-102)

- Ce qui est posé dans le monde est l'**état de la zone** de son module : la publication d'une nouvelle version appelle
  l'`apply` du module, qui fait `move` (lieu, rayon), `replace` (nouvelle définition entière : nœuds ajoutés, retirés)
  ou `set` (un réglage) ; création → `define`, suppression → `remove`. Les joueurs proches voient le changement sans
  redémarrage ; les autres le reçoivent en arrivant (critère de T-102 « un joueur loin ne reçoit rien », lu par
  `/vava_reseau joueur` et `/vava_reseau zones`).
- Une définition en **essai** n'entre pas dans l'état de la zone (sinon tous les abonnés la verraient) : elle part par
  `core.net.send` à son seul auteur.
- Les catalogues (gestes, effets, sorts, techniques) ne sont pas des zones : envoyés une fois avec un numéro de
  version, par RPC ou `sendPacked` (latent au-delà de 8 Ko, plafond global).
- Une zone de récolte avec 50 nœuds définis (~6 Ko) reste sous le seuil du latent ; au-delà, le préavis et le tampon
  du client gardent l'ordre.

Rappel des propositions acceptées :

1. **Entrée décidée par le serveur, pas demandée par le client.** Le backlog et `SECURITE_RESEAU.md` disaient « le client
   entre dans le rayon → il la demande (RPC limité) ». Pour demander, le client devrait connaître toutes les zones
   (centres, rayons) : un annuaire envoyé à tous et tenu à jour à chaque création du Conseil, ce qu'on veut justement
   éviter ; et le serveur devrait de toute façon revérifier la distance à chaque demande. Ici, le serveur lit une
   position par joueur et par seconde et cherche dans une grille : moins de 0,2 ms, aucune boucle côté client, aucun RPC
   d'abonnement à protéger. Le client ne garde qu'un RPC pour redemander un instantané d'une zone qu'il suit déjà.
2. **Cercle horizontal seulement.** Distance au sol (la hauteur ignorée) : mines, collines et étages restent dans la
   zone ; un polygone (parcelle de T-103) donne son cercle englobant. Une zone n'a jamais besoin d'une forme exacte
   pour l'abonnement : le module garde sa propre géométrie pour ses règles (voix : cylindre, parcelle : emplacements).
3. **État tenu par le core** (paires clé → valeur, révision), plutôt qu'un instantané demandé au module à chaque
   entrée : aucun aller-retour vers le module, une seule sérialisation pour tous les entrants d'un passage, rien de gros
   ne traverse l'export. Contrepartie : le module écrit ce qu'il publie dans le core (`set`), comme il l'écrit
   aujourd'hui dans GlobalState.
4. **`sendPacked` plutôt qu'une bibliothèque chargée par chaque module.** La bibliothèque proposée par la relecture
   (`@vAvA_core/shared/…`) dupliquerait dans chaque module la validation des cibles, demanderait quand même au core la
   réservation du latent et l'écriture au compteur, et ajouterait une globale par module (contraire à `CLAUDE.md`).
   Avec `sendPacked`, le module sérialise, une chaîne traverse l'export (copie d'un bloc, sans parcours), et le core
   reste seul à décider (cibles, plafonds, compteur). Personne ne s'en sert dans cette tâche : la bascule des modules
   sur `core.net` (déjà relevée par T-013) l'utilisera.
5. **Réglages** : passage de 1 s, marge par défaut de 50 m, hystérésis de 25 m, cases de 256 m, 32 Ko d'instantanés
   par joueur et par passage, plafond global du latent de 4 Mo, 2 048 zones (1 024 par module), 32 Ko par zone.
6. **Voix** : marge de 40 m ; l'éditeur d'un membre du Conseil se met à jour seul pour les zones proches changées par
   un autre, et pour les lointaines à sa réouverture (aujourd'hui tout arrive à tout le monde). La liste complète de
   l'éditeur reste envoyée au seul membre qui l'ouvre.
7. **`/vava_reseau zones <n°>`** inscrit au journal du Registre (il révèle à peu près où se trouve un joueur), comme
   `joueur <n°>` ; la vue d'ensemble non.
8. **Toutes les instances par défaut** : une zone sans `bucket` est suivie par les joueurs de tous les routing buckets
   (même règle que `sendNear`, décision 7 de T-013).
