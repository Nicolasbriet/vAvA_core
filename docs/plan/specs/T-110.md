## 1. But joueur

Un coup d'épée, une boule de feu, la faim ou une chute : quoi qu'il arrive, c'est le royaume qui tient le compte de vos
blessures, pas votre jeu. Un bouclier de givre arrête aussi bien une lame qu'un trait de feu, une parade annule un coup,
et personne ne peut se rendre invulnérable en trafiquant son client. Celui qui tombe a besoin des autres pour se relever.

Piliers du lore : « Personne ne sait tout faire » (on se relève par les autres, on se protège par la magie d'un autre,
la défense est un savoir) ; « La magie : prudence, coût, conséquences » (les protections deviennent des modificateurs
réglés, jamais gratuits) ; « Les objets portent des histoires » (le paquet de dégât porte l'arme et la technique qui
ont frappé, gardées au journal).

## 2. Périmètre

### 2.1 Dedans

- **Vie tenue par le serveur** : `entry.health` devient la valeur de référence ; le client l'applique, le serveur relit
  le ped pour détecter les pertes natives (chute, noyade…) et corriger un client qui garde plus de vie qu'il n'en a ;
  mise à terre décidée par le serveur dès que sa valeur atteint 0.
- **Export `hit(cible, paquet)`** : paquet borné et validé (§ 5.1), garde-fous (débit par cible, profondeur,
  interrupteur des dégâts entre joueurs), hook `vava_health:hit` `before` puis modificateurs puis application puis hook
  `after`, résultat chiffré.
- **Registre `vava_health:modifiers`** : six étapes ordonnées, priorité dans l'étape, appels isolés et chronométrés
  (§ 5.2).
- **Journal des coups** `vava_health_hits` (migration `0001`), écrit par lots.
- **Annulation des dégâts natifs entre joueurs** côté serveur (`weaponDamageEvent`, plus explosions, feux et projectiles
  lancés par un joueur), protections du client à chaque apparition.
- **Porte `spawned`** : plus aucune écriture de la vie n'en dépend ; lecture du ped d'office après un délai si le client
  ne confirme pas son apparition.
- **Compatibilité** : `damage` devient une enveloppe de `hit` ; `vava_needs` passe à `hit` (`privation`).
- **Ressource d'exemple** `examples/vava_example_combat` (mode développement seulement) : frapper, modificateurs d'essai,
  arme et explosion natives pour vérifier l'annulation, liste de la chaîne.
- Tests unitaires (paquet, ordre et pas de la chaîne, jugement d'une lecture, porte d'apparition, harnais de `hit`) et
  procédure en jeu `docs/tests/combat.md` § 1.

## 5. Données

### 5.1 Le paquet de dégât (argument de `hit`)

```lua
exports.vava_health:hit(target, {
    amount = 12,                  -- obligatoire : points avant modificateurs, nombre fini, 0 < amount ≤ chain.maxAmount
    kind = 'tranchant',           -- obligatoire : un de chain.kinds
    source = attackerSrc,         -- facultatif : joueur à l'origine (entier 1 à 65535) ; nil : le monde, la faim…
    sourceCharacter = 42,         -- facultatif : personnage à l'origine (entier ≥ 1), quand le joueur a pu partir
    part = 'torse',               -- facultatif : un de chain.parts
    weapon = 'epee_longue',       -- facultatif : objet d'inventaire qui a frappé (identifiant ≤ 64 octets)
    technique = 'taille_descendante', -- facultatif : technique de vava_combat (identifiant ≤ 64 octets)
    spell = 'boule_de_feu',       -- facultatif : sort (identifiant ≤ 64 octets)
    tags = { melee = true, parryable = true },  -- facultatif : map étiquette → true, chain.tags, ≤ chain.maxTags
})
```

Règles (`shared/packet.lua`, `packet.normalize(raw, limits)` → copie normalisée ou `nil, code`) :
- `raw` doit être une table à clés nommées ; toute clé hors de la liste ci-dessus → `unknown_field` (en particulier
  `origin` : jamais fourni par l'appelant) ;
- `amount` : `type == 'number'`, ni `NaN` ni `±inf`, `> 0`, `≤ maxAmount` → sinon `invalid_amount` ;
- `kind` : dans `kinds` → sinon `invalid_kind` ;
- `source` : entier 1 à 65 535 ; `sourceCharacter` : entier ≥ 1 et ≤ 2³¹ − 1 → sinon `invalid_source` ;
- `part` : dans `parts` → sinon `invalid_part` ;
- `weapon`, `technique`, `spell` : chaîne de 1 à 64 octets au motif des identifiants du core `^[%w_%-%.:]+$` (les
  identifiants de l'Atelier `<éditeur>:<id>` passent) → sinon `invalid_ref` ;
- `tags` : table dont chaque clé est dans `tags` et chaque valeur vaut exactement `true`, au plus `maxTags` clés, aucune
  clé entière (pas de liste) → sinon `invalid_tags` ;
- autre chose qu'une table → `invalid_packet`.

Le serveur complète la copie, sans rien demander à l'appelant :
- `origin` = `GetInvokingResource()` (la ressource qui appelle l'export ; `vava_health` pour ses propres appels) ;
- `id` = numéro de coup (entier croissant, repart à 1 après 2³¹ − 1) ;
- `sourceCharacter` = personnage actif de `source` s'il est en jeu (prime sur celui du paquet), sinon celui du paquet,
  sinon nil.

### 5.2 Le registre `vava_health:modifiers`

Défini par `vava_health` dans son `setup` (`core.registry.define`, `maxEntries = chain.maxModifiers`). Clé :
`<ressource>:<nom>` (motif `^[%w_]+:[%w_%-]+$`, 64 octets) ; une entrée ajoutée par une autre ressource que celle du
préfixe est retirée aussitôt (hook `core:registry:added`, comme `vava_atelier:editors`), avec une ligne de console.

```lua
core.registry.add('vava_health:modifiers', 'vava_magic:protections', {
    stage = 'bouclier',          -- obligatoire : étape (ci-dessous)
    priority = 50,               -- facultatif : 0 à 99 dans l'étape (défaut 50) ; plus petit = plus tôt
    label = 'Protections magiques', -- obligatoire : 1 à 48 octets (console, journal, /chaine)
    kinds = { 'feu', 'eau' },    -- facultatif : appelé seulement pour ces types (1 à 11 valeurs de chain.kinds)
    apply = function(ctx) return nil end,  -- obligatoire : le modificateur (§ 7.2)
})
```

Schéma du registre : `{ type = 'table', fields = { stage = { type = 'string', enum = STAGES }, priority = { type =
'integer', min = 0, max = 99, optional = true }, label = { type = 'string', min = 1, max = 48 }, kinds = { type =
'array', min = 1, max = 11, items = { type = 'string', enum = chain.kinds }, optional = true }, apply = { type =
'function' } } }` (strict) ; validateur : `chain.checkEntry(key, data)` (motif de la clé, `kinds` sans doublon).

Étapes, dans l'ordre fixe de `COMBAT_V1.md` (constantes, pas de config : l'ordre est une règle) :

| Rang | `stage` | Pour quoi | Tâche qui la remplit |
|---|---|---|---|
| 1 | `annulation` | cible intouchable (zone sûre, invulnérabilité, essai) | T-116 (zones protégées), tâche § 13-1 (Registre) |
| 2 | `esquive` | fenêtre d'invulnérabilité | T-113 |
| 3 | `parade` | coup annulé, l'attaquant chancelle | T-113 |
| 4 | `blocage` | réduction selon bouclier ou arme, coût d'endurance | T-113, T-114 |
| 5 | `bouclier` | absorption (Égide de givre…) | T-116, T-123 |
| 6 | `resistance` | résistance ou faiblesse à un type (armure plus tard) | T-116, T-123 |
| 7 | application | vie serveur, mise à terre, hook `after` | `vava_health` (§ 7.1) |

Ordre d'appel : rang de l'étape, puis `priority`, puis clé (ordre alphabétique : stable et reproductible). Le cache trié
est reconstruit (copie, jamais en place) à chaque ajout ou retrait ; un coup en cours garde sa liste.

**Un module déclare au plus un modificateur par étape**, qui lit ses propres données (protections actives d'un joueur,
fenêtres ouvertes, définitions de l'Atelier) : les données changent sans toucher au registre (§ 12.3).

Un module déclare ses modificateurs dans son `setup` si `core.registry.exists('vava_health:modifiers')`, et de nouveau sur
`core:module:ready` quand `name == 'vava_health'` (le registre disparaît avec `vava_health` à son arrêt). L'exemple du § 9
le montre.

### 5.4 Migration `sql/0001_hits.sql`

Aucun `?` dans le fichier (oxmysql le lirait comme un paramètre).

```sql
-- vava_health : journal des coups (chaîne de dégâts). Dates en secondes (horloge du serveur). Points sur 100.
CREATE TABLE IF NOT EXISTS `vava_health_hits` (
    `id` BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
    `at` INT UNSIGNED NOT NULL,
    `target_id` INT UNSIGNED NOT NULL,              -- personnage touche
    `source_id` INT UNSIGNED NULL DEFAULT NULL,     -- personnage a l'origine ; NULL : le monde, la faim
    `origin` VARCHAR(64) NOT NULL,                  -- ressource qui a appele hit (vava_health : perte native)
    `kind` VARCHAR(16) NOT NULL,
    `ref` VARCHAR(64) NULL DEFAULT NULL,            -- technique ou sort
    `weapon` VARCHAR(64) NULL DEFAULT NULL,
    `amount` DECIMAL(6,1) NOT NULL,                 -- avant modificateurs
    `applied` DECIMAL(6,1) NOT NULL,                -- retire de la vie
    `blocked` DECIMAL(6,1) NOT NULL DEFAULT 0,
    `absorbed` DECIMAL(6,1) NOT NULL DEFAULT 0,
    `resisted` DECIMAL(6,1) NOT NULL DEFAULT 0,
    `cancelled` VARCHAR(32) NULL DEFAULT NULL,      -- raison d'une annulation
    `downed` TINYINT(1) NOT NULL DEFAULT 0,
    `x` FLOAT NULL DEFAULT NULL,
    `y` FLOAT NULL DEFAULT NULL,
    `z` FLOAT NULL DEFAULT NULL,
    PRIMARY KEY (`id`),
    KEY `idx_vava_health_hits_at` (`at`),
    KEY `idx_vava_health_hits_target` (`target_id`, `at`),
    KEY `idx_vava_health_hits_source` (`source_id`, `at`)
) ENGINE = InnoDB DEFAULT CHARSET = utf8mb4 COLLATE = utf8mb4_unicode_ci;
```

Ce qui est inscrit : tout coup **venu d'un autre joueur** qui a atteint la chaîne (annulé compris), et **toute mise à
terre** par la chaîne ou par une perte native. Ne sont pas inscrits : les coups sans source qui ne mettent pas à terre
(faim, chute), les coups refusés (`nil, code`), les coups sur une cible déjà à terre. Position lue côté serveur au
moment du coup. Requêtes (`core.db`, paramétrées) : `INSERT … VALUES (?, …)` répété par lot (le patron de
`vava_magic/server/combat.lua`, `rep(ROW, n, ', ')` : seuls des groupes de `?` sont répétés) ; purge
``DELETE FROM `vava_health_hits` WHERE `at` < ? LIMIT ?`` par lots de 5 000, une seconde entre deux.

### 5.5 Mémoire du serveur

Entrée de `life` (une par personnage chargé) complétée : `syncUntil` (lecture ignorée avant), `pushPending` (un `SET`
déjà prévu ce tour), `dirty` (vie à écrire dans le champ), `correctedAt`, `corrections`, `spawnOrderedAt`,
`forcedSpawn`. Chaîne : compteur de coups par cible sur une seconde glissante (`{ count, since }`), profondeur courante,
numéro de coup. Journal : file bornée (`journal.queueMax`). Natifs : compteur d'annulations par joueur (une ligne par
minute). Tout est retiré au déchargement et au départ ; borné par le nombre de joueurs.

## 6. Réseau

**Aucun RPC nouveau.** `vava_health:assist` et `vava_health:giveUp` inchangés (schéma `{}`, débits de la config).

### 6.2 Évènements serveur → client

Tous les envois de `vava_health` passent désormais par `VavaHealth.send` → `core.net.send(cible, …)` (comptés dans
`/vava_reseau`, fiables), repli `TriggerClientEvent(nom, cible, …)` vers ce seul joueur si `core.net` manque.

| Évènement | Valeurs | Cible (qui, pourquoi) | Taille | Fréquence |
|---|---|---|---|---|
| `vava_health:set` | part de vie (nombre) | le **seul** joueur dont la vie serveur a changé (coup, soin, `setHealth`), ou dont le ped est lu au-dessus de la valeur serveur (correction) | ≈ 26 o | une fois par tour au plus par joueur (les coups d'un même tour sont regroupés, § 7.1) ; correction au plus toutes les 2 s, seulement à un client en retard ou modifié |
| `vava_health:down` | — | le seul joueur mis à terre | ≈ 17 o | inchangé (mise à terre, renvoi toutes les 5 s à un ped resté debout) |
| `vava_health:revive`, `respawn`, `channel`, `message` | inchangés | inchangés | inchangés | inchangés |
| champ `vava_health:state` (`owner`) | `{ health, downed, downedFor }` | le seul joueur | ≈ 40 o | à chaque transition, aux soins, et au plus toutes les 10 s après des coups (écriture différée, § 7.1) |

**Rien à personne d'autre** : ni l'attaquant ni les proches ne reçoivent quoi que ce soit de `vava_health`. Le résultat
de `hit` revient au **module appelant**, qui décide de ce qu'il montre (T-112 enverra la réaction aux proches par
`core.net.sendNear`, `from = attaquant` ; la magie garde son `vava_magic:hit` vers la cible). Aucun `-1`, aucun
GlobalState, aucun state bag, aucun envoi latent.

Coûts : un coup = un `SET` de ≈ 26 o à la cible ; un combat à six (≈ 1 coup reçu par seconde chacun) ≈ 160 o/s pour
tout le serveur, plus un champ de ≈ 40 o par joueur et par 10 s. Un client honnête ne reçoit aucune correction.

## 7. Vérifications serveur

### 7.1 `hit(target, paquet)` (export, `server/chain.lua`)

Dans l'ordre, **sans céder la main** entre la lecture de la vie et son écriture (aucun `Wait`, aucune base) :

1. `VavaHealth.ready`, sinon `nil, 'not_ready'` ; `target` entier, sinon `invalid_target` ; personnage suivi
   (`life.entry`), sinon `no_character`. **Aucune condition sur `spawned`.**
2. `packet.normalize` (§ 5.1), sinon `nil, code` ; `origin`, `id`, `sourceCharacter` posés par le serveur.
3. Profondeur : `depth ≥ maxDepth` → `nil, 'too_deep'`. Débit : plus de `maxHitsPerSecond` coups sur cette cible dans
   la seconde → `nil, 'too_many_hits'`.
4. Préconditions (rendent un résultat annulé, sans hook ni journal) : cible à terre → `cancelled = 'downed'` ;
   `chain.pvp == false` et `source` présent et différent de la cible → `cancelled = 'pvp_off'`.
5. Contexte `ctx` : `{ id, target, targetCharacter, source?, sourceCharacter?, origin, kind, amount, base = amount,
   part?, weapon?, technique?, spell?, tags, health = vie de la cible en points }`.
6. `core.hooks.runBefore('vava_health:hit', ctx)` : refus → `cancelled = raison` (ou `hook_error`), `stage = 'before'`,
   puis directement l'étape 9 (hook `after`, journal).
7. Modificateurs (`chain.run`, § 7.2) : chacun reçoit `ctx` avec le montant courant et l'étape ; arrêt à la première
   annulation.
8. Application : la cible est **relue** (`life.entry`, toujours la même entrée, pas à terre entre-temps : sinon
   `cancelled = 'downed'`, `stage = 'application'`) ; `applied = min(montant final, vie en points)` ;
   `life.applyLoss(target, applied / healthPoints)` : `entry.health` baisse, `dirty = true`, `SET` prévu pour la fin du
   tour (`pushPending`, un seul `SetTimeout(0)` par joueur et par tour, valeur relue au moment de l'envoi), `syncUntil`
   repoussé (§ 7.3). Vie serveur à 0 → `life.down(target, 'hit', kind, source)` **aussitôt** (ordre `DOWN`, hook
   `vava_health:downed` avec `origin` et `hitId` en plus), sans attendre la lecture du ped.
9. `core.hooks.runAfter('vava_health:hit', ctx + résultat)` pour **tout coup qui a atteint l'étape 6** (annulé
   compris) ; journal (§ 5.4) ; profondeur rendue (dans un `pcall` : jamais laissée haute après une erreur).
10. Retour : `{ id, amount (après modificateurs), applied, blocked, absorbed, resisted, added, cancelled?, stage?,
    downed, health (part 0 à 1 après le coup) }`.

Coup lent (`slowHitMs`) : une ligne de console limitée. Le coup n'est jamais coupé en route.

### 7.2 Un modificateur (`shared/chain.lua`)

`apply(ctx)` reçoit une **copie** (traversée d'export) et ne modifie rien : il **rend un résultat**.

| Rendu | Effet (borné par `chain.step`) |
|---|---|
| `nil` ou `true` | rien |
| `{ cancel = 'raison' }` | montant à 0, `cancelled = raison` (motif `^[%w_]+$`, 32 octets ; sinon `'cancelled'`), `stage` = étape ; aucun modificateur suivant |
| `{ blocked = n }` | `n` retiré du montant (au plus le montant courant), compté en `blocked` |
| `{ absorbed = n }` | idem, compté en `absorbed` |
| `{ resisted = n }` | idem, compté en `resisted` |
| `{ added = n }` | ajouté au montant (faiblesse, « fragiliser ») : au plus le montant de départ (`base`) par modificateur, total au plus `maxAmount` ; compté en `added` |

Plusieurs champs dans un même rendu : `cancel` d'abord (le reste est ignoré), sinon `blocked`, `absorbed`, `resisted`,
`added` dans cet ordre. Un nombre non fini, négatif ou un autre type rend **tout** le rendu ignoré (console limitée,
`invalid_result`). L'étape ne restreint pas les champs : elle fixe seulement l'ordre (un blocage rend `blocked`, un
bouclier `absorbed`, par convention documentée).

Isolement : chaque appel est fait par `pcall`, chronométré (`GetGameTimer`). Erreur → **ce modificateur est ignoré pour
ce coup**, les suivants s'exécutent, une ligne d'erreur par modificateur et par `errorLogMs` (décision 7). Plus lent que
`slowModifierMs` → signalé. Contrat écrit dans le README : un modificateur ne cède jamais la main (`Wait`, base,
`callClient`) et ne lance pas `hit` lui-même (le hook `after` sert aux renvois).

Filtre : un modificateur qui déclare `kinds` n'est appelé que pour ces types.

### 7.3 Lecture du ped et client qui ment (`server/life.lua`, boucle existante de 500 ms)

Règles pures dans `shared/sync.lua` :
- `sync.window(now, applyMs, ping, maxPingMs)` = `now + applyMs + min(2 × ping, maxPingMs)` ; posée à chaque envoi de
  `SET`, `REVIVE`, `RESPAWN` (ping : `GetPlayerPing(src)`).
- `sync.judge(observed, reference, now, syncUntil, tolerance)` → `'wait'` (avant `syncUntil`), `'ok'` (écart ≤
  tolérance), `'loss', écart` (ped plus bas), `'above'` (ped plus haut).
- `sync.spawnGate(entry, now, pedExists, confirmTimeoutMs)` → `'read'` (apparition confirmée), `'forced'` (non confirmée,
  délai passé depuis `spawnOrderedAt`, ped présent), `'wait'`.

Pour chaque joueur suivi, à chaque passage :

| Cas | Décision |
|---|---|
| Apparition non confirmée | `spawnGate` : `'forced'` → `spawned = true`, grâce `graceMs`, console une fois par chargement « joueur N : apparition non confirmée après 20 s, vie lue d'office » ; `'wait'` → rien |
| À terre | inchangé (temps compté, retour d'office, ped debout recouché toutes les 5 s) |
| Délai de grâce | rien |
| Ped lu au seuil ou dessous (`vitality.fallen`) | perte native mortelle : `life.applyLoss` de toute la vie restante, hook `after` (`origin = 'vava_health'`, `kind = 'monde'`, `tags = { native = true }`), `life.down(src, 'death', GetPedCauseOfDeath, killerOf)` comme avant, journal ; si `killerOf` trouve un joueur : console « mise à terre par un coup natif du joueur N (hors chaîne) » (ne devrait plus arriver) |
| `'loss', écart` | perte native (chute, noyade, feu du décor, animal, véhicule) : appliquée telle quelle, **sans `before` ni modificateurs** (décision 9), hook `after` comme ci-dessus ; pas de journal (sans source, pas à terre) |
| `'above'` | correction : `SET` de la valeur serveur si `now − correctedAt ≥ resendMs` ; `corrections + 1` ; console à la 1re puis toutes les `logEvery` (« joueur N : vie du client au-dessus de celle du serveur (k fois), remise ») |
| `'ok'`, `'wait'` | rien |

Écriture du champ : **différée** pour les coups et les pertes (`dirty`, écrit au passage suivant si `now − sampledAt ≥
sampleMs`) ; **immédiate** pour une mise à terre, une relève, un retour au lieu de soins, un soin, `setHealth` ; au
départ (`core:character:unloading`, priorité 10, inchangée) et à l'arrêt du module (`onResourceStop` →
`life.persistAll()`, l'API reste servie en `stopping`). La boucle n'écrit plus jamais la vie **lue sur le ped** dans le
champ : seule la valeur serveur l'est.

Ce qu'un client modifié peut encore faire, et ce que ça lui rapporte :
- ignorer `SET` ou se remettre à plein : rien (la valeur serveur fait foi pour `hit`, `isDowned`, `get`, les soins, la
  mise à terre ; correction toutes les 2 s, console) ;
- refuser `DOWN` : rester debout à l'écran (limite connue, § 12) ; tout ce qui compte est refusé par `isDowned` ;
- se baisser lui-même : il ne fait de tort qu'à lui ;
- ne pas confirmer son apparition : lu d'office après 20 s.

### 7.4 Annulation des dégâts natifs (`server/natives.lua`)

Branchés dans `setup` par `AddEventHandler` (évènements du moteur OneSync, **pas** des `RegisterNetEvent`), chacun en
quelques natives :

| Évènement | Décision |
|---|---|
| `weaponDamageEvent(sender, data)` | victimes : `data.hitGlobalIds` (liste) ou `data.hitGlobalId` ; pour chacune, `NetworkGetEntityFromNetworkId` ; victime existante, ped (`GetEntityType == 1`), joueur (`IsPedAPlayer`) et dont le propriétaire n'est pas `sender` (`NetworkGetEntityOwner`) → `CancelEvent()` ; victime introuvable (id 0, entité absente) et `natives.unresolved` → `CancelEvent()` ; PNJ, animal, objet → laissé |
| `explosionEvent(sender, ev)` | `natives.explosions` → `CancelEvent()` |
| `fireEvent(sender, ev)` | `natives.fires` → `CancelEvent()` |
| `startProjectileEvent(sender, data)` | `natives.projectiles` → `CancelEvent()` |

Chaque annulation compte pour `sender` ; au plus une ligne `info` par joueur et par minute (« joueur N : k coups natifs
annulés (poings, armes), m explosions… »). Logique pure testable : `natives.victims(data)` (liste des identifiants) et
`natives.decide(victims, sender, lookup, cfg)` dans `server/natives.lua` avec `lookup` injecté.

Ce qui reste natif, lu par le serveur comme une perte « monde » (§ 7.3) :

| Source | Traitement |
|---|---|
| Coups de poing, d'arme, de couteau entre joueurs | **annulés** (serveur) ; client : tir ami coupé |
| Explosions, feux, projectiles lancés par un joueur | **annulés** (serveur) |
| Chute, noyade, feu du décor | natifs, lus |
| Véhicule (choc, renversé) | natif : physique locale de la victime, aucun évènement à annuler ; aucun véhicule à Eldoria ; à revoir avec les montures |
| PNJ, animaux du monde | natifs (aucune créature hostile en v1) |
| Coups de `vava_combat`, sorts, faim | **chaîne** |

`gameEventTriggered` / `CEventNetworkEntityDamage` côté client n'est **pas** utilisé : il ne dirait au serveur que ce que
le client veut bien dire ; la lecture serveur suffit. `SetEntityCanBeDamaged` et `SetEntityProofs` ne sont pas utilisés :
ils couperaient aussi la chute et la noyade.

## 12. Risques, et ce qui est laissé aux tâches suivantes

### 12.1 Risques et comment la spec les ferme

| Risque | Fermeture |
|---|---|
| Client qui ignore `SET` ou se remet à plein (rapport T-006, IMPORTANT 1 de l'audit) | la vie serveur fait foi pour tout ; ped lu au-dessus → `SET` toutes les 2 s, console ; la mise à terre ne dépend plus du ped |
| Client qui ne confirme pas son apparition (IMPORTANT 2) | aucune écriture de la vie ne dépend de `spawned` ; lecture du ped d'office après 20 s |
| Coups natifs entre joueurs (poings, armes données par un menu de triche, explosions, feux, projectiles) | annulés côté serveur avant d'atteindre la victime ; compteur et console par joueur |
| Module qui se fait passer pour un autre (journal, conditions sur `origin`) | `origin` = `GetInvokingResource()`, refusé dans le paquet |
| Paquet piégé (NaN, infini, chaînes géantes, tables imbriquées, clés en trop) | schéma fermé et borné (`shared/packet.lua`, testé) |
| Modificateur en erreur, lent ou piégé (rendu négatif, NaN) | `pcall`, rendu borné par une fonction pure, erreur ignorée pour ce coup, console limitée ; jamais d'invulnérabilité par une panne |
| Modificateur déclaré au nom d'un autre module | préfixe de la clé = ressource propriétaire, sinon retiré |
| Boucle de renvois (épines contre épines) | profondeur 2 |
| Avalanche de coups (zone qui tique sur 20 joueurs, bug d'un module) | 20 coups par seconde et par cible ; coût d'un coup ≈ 0,1 à 0,3 ms avec six modificateurs |
| Courses (deux coups simultanés, cible relevée ou partie pendant un coup) | aucune attente entre lecture et écriture ; cible relue à l'application |
| Soin pris pour une perte (client pas encore à jour) | fenêtre d'application de 1,5 s + 2 × ping |
| Saturation de la base par le journal | seuls les coups venant d'un joueur et les mises à terre ; lots de 50 ; file bornée ; purge 30 jours |
| Perte de la vie entre deux écritures (écriture différée) | écrite à chaque transition, au départ, à l'arrêt du module ; au plus 10 s perdues sur un plantage du serveur (comme aujourd'hui) |
| Envoi à tous | aucun : `SET` à la seule cible, rien à l'attaquant ni aux proches |
| **Limite connue** : un client modifié qui refuse `DOWN` reste debout à l'écran | rien de ce qui compte ne lui est permis (`isDowned` partout côté serveur), recouché toutes les 5 s, console ; un serveur FiveM ne peut pas imposer la vie d'un ped joueur |
| `vava_health` arrêté | plus d'annulation des coups natifs ni de chaîne pendant l'arrêt (comme toute la santé) ; à ne jamais arrêter sur un serveur ouvert |

### 12.2 Laissé à T-111 … T-116

- **T-111** : coupe le corps à corps natif et les armes à feu (l'annulation serveur reste en filet) ; dégâts de base d'un

  `contondant` pour masse et bâton, `percant` pour dague).

  `hit` à l'ouverture de la fenêtre, envoie le résultat à l'attaquant et la réaction aux proches (`core.net.sendNear`,
  `from`).
- **T-113** : trois modificateurs `vava_combat:esquive`, `vava_combat:parade` (rend `{ cancel = 'parade' }` et fait
  chanceler l'attaquant par les états de `vava_magic`), `vava_combat:blocage` (`{ blocked = … }`, angle de face, coût
  d'endurance) ; tous respectent `unblockable` / `undodgeable`.
- **T-114** : endurance ; un coup reçu peut en coûter par le hook `after`.
- **T-115** : XP de combat sur le hook `after` (`applied > 0`, `source` réel, cible joueur).
- **T-116** : `combat.damage` de la magie appelle `hit` par son bridge (`amount = points`, `kind` = élément du sort,
  `source`, `sourceCharacter`, `spell`, `tags = { spell, area? , overTime? (brûlure) }`) au lieu de `damage` ; ne
  déclenche réaction, brûlure et XP que si `applied > 0` ; `combat.protectedZones` devient le modificateur

  les protections actives ; repli sans `vava_health` (évènement `vava_magic:damage` au client) à trancher par T-116.

## 13. Points à remonter au porteur du projet

1. **Invulnérabilité du Registre** (`vava_admin`, outil « Invulnérabilité » : « Rien ne peut vous mettre à terre ») :
   elle n'est que locale (`SetEntityInvincible`) et ne protégeait déjà pas des sorts (`damage` → `SET`). Avec la chaîne,
   un coup d'épée la traversera aussi. Proposition de tâche (fin de phase 4, après T-110) : `vava_admin` garde côté
   serveur l'état « invulnérable » (outil `godmode`, observation en cours) et déclare le modificateur
   `vava_admin:invulnerabilite` (étape `annulation`, priorité 10). Petite, mais elle touche `vava_admin`.
2. **Confirmation de l'apparition par le core** (option B de la porte) : utile à tous (temps de jeu, positions,
   `vava_arrival`, envois de proximité), qui croient tous encore la déclaration du client. Proposition de tâche du core :
   `spawn.send` garde le point ordonné ; la boucle des positions confirme d'office un personnage dont le ped est à
   moins de 5 m de ce point depuis 10 s (hook `core:character:spawned` avec `forced = true`). Demande l'autorisation
   de toucher `server/players/`.
3. **Limite assumée** : un client modifié peut garder son ped debout à l'écran alors qu'il est à terre pour le serveur
   (rien ne lui est permis, il est recouché toutes les 5 s) ; aucun serveur FiveM ne peut imposer la vie d'un ped
   joueur.
4. **Combats entre joueurs** : `chain.pvp = true` par défaut (comme `combat.pvp` de la magie). À couper d'un réglage si
   le porteur veut un royaume sans violence entre joueurs avant la porte T-119.
