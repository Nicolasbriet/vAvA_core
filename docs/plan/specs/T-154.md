## 1. But joueur

Rien ne change en jeu. À sa première connexion, chaque joueur télécharge **≈ 400 à 450 Ko de Lua en moins**
(≈ 180 à 200 Ko compressés, ≈ un tiers du Lua livré) ; et quand un développeur retouche un commentaire d'un fichier
client, plus rien n'est retéléchargé ni redémarré : le fichier livré n'a pas changé. Le dépôt, lui, reste commenté.

Lien au lore : aucun pilier n'est touché (aucune mécanique, aucun texte vu des joueurs). C'est la règle « Bande passante :
ne rien envoyer à qui n'en a pas besoin » du socle, appliquée aux fichiers servis, après T-132.

## 5. Ce qui est allégé, ce qui ne l'est jamais

### 5.1 Règle

Pour chaque ressource (racine `vAvA_core`, chaque `modules/*` et `examples/*` à manifeste — la disposition de
`installer.layout`), un fichier est **allégé** si et seulement si :

| # | Condition |
|---|---|
| 1 | c'est le `fxmanifest.lua` de la ressource (servi à chaque joueur) ; **ou** |
| 2 | il est désigné par une chaîne de `shared_script`, `shared_scripts`, `client_script` ou `client_scripts` (même s'il l'est aussi par `server_script(s)`), chemin en `.lua` (casse de l'extension ignorée), dans la ressource, **et** n'est pas un réglage de l'exploitant : `userOwned(chemin)` faux (nom de base `config.lua` ou `config_client.lua`, ou chemin sous `config/`) ; **ou** |
| 3 | il est désigné par une chaîne de `vava_conseil_lua` (T-157 : Lua du paquet du Conseil, exécuté chez les membres), chemin en `.lua`, dans la ressource, **et** `userOwned(chemin)` faux (`config.lua` y est de toute façon refusé par l'audit de T-157) ; `config_conseil.lua` n'est pas un `userOwned` : il **est** allégé (il part dans le paquet, § 16-13), même s'il est aussi en `server_scripts` ; |
| 4 | **et** il se lit (§ 6.3) et passe son contrôle (§ 6.5) ; sinon il est laissé tel quel et signalé. |

Un fichier du paquet qui est aussi lu par le serveur (`config_conseil.lua`, `shared/placerules.lua` chez T-157) est
allégé sur le disque : le serveur lit donc la même version que les membres, aux mêmes lignes.

### 5.3 Lecture du manifeste (`delivery.servedLua(resourceDir)`)

Même lecture que `scripts/lib/manifeste.awk`, faite sur les évènements du lexeur (commentaires ignorés, chaînes courtes
et longues lues). Constantes de `delivery.js` : `TRACKED_DIRECTIVES` (les douze directives suivies ci-dessous),
`LEAN_DIRECTIVES = ['shared_script', 'shared_scripts', 'client_script', 'client_scripts']` (Lua servi à la connexion,
réglages exclus), `COUNCIL_DIRECTIVES = ['vava_conseil_lua']` (Lua du paquet du Conseil, réglages exclus de même),
`MAX_BYTES = 4 * 1024 * 1024`.

- Directives suivies : `files`, `file`, `ui_page`, `loadscreen`, `shared_script(s)`, `client_script(s)`,
  `server_script(s)`, `vava_conseil_lua`, `vava_conseil_web` ; forme simple (`client_script 'a.lua'`, `client_script('a.lua')`, `client_script [[a.lua]]`) ou
  table (`{ … }`, tables imbriquées, virgules et points-virgules), parenthèses permises autour.
- Une directive suivie d'autre chose qu'une chaîne ou une table de chaînes (nom, concaténation `..`, appel, index) :
  **forme illisible** → **toute la ressource est laissée telle quelle** et signalée (dans le dépôt, l'audit refuse déjà
  ces formes : règle X de T-132).
- Chaque chaîne est normalisée comme `norm()` de l'awk (`\` → `/`, `//` réduit, `./` et `/./` retirés, `/` de tête
  retiré ; une chaîne longue perd ses fins de ligne). `@…` ignoré. `x/../` réduit ; un chemin qui sortirait de la
  ressource est ignoré (règle D de l'audit).
- Jokers : `*` (hors `/`), `?` (un caractère hors `/`), `[…]`, `**` (zéro ou plusieurs dossiers) — sémantique de `bash`
  avec `globstar`, celle de `poids-client.sh` ; développés sur la liste des fichiers de la ressource (`.git` exclu).
  Sans joker : le fichier existe (`fs.existsSync`, donc insensible à la casse sous Windows, comme `bash`).
- Résultat : `{ ok: true, files: [{ path, state, council }] }`, `path` relatif à barres obliques, dans l'ordre de
  première rencontre, sans doublon ; `state` : `lean` (allégé), `kept-config` (réglage), `kept-files` (désigné par
  `files` ou `file` seulement) ; `council` vrai pour un fichier de `vava_conseil_lua` (un même fichier peut figurer deux
  fois, une fois de chaque côté, comme dans `poids-client.sh`). `fxmanifest.lua` en tête, `lean`. Ou
  `{ ok: false, reason }`.

La liste est **recoupée à chaque vérification** avec celle de `poids-client.sh --liste` (qui lit par `manifeste.awk`) :
deux lecteurs, une seule vérité, tout écart est un échec (§ 10.3).

## 6. L'allègement (`chancellerie/lib/luastrip.js`)

### 6.1 Entrée et sortie

Le fichier est lu en `Buffer`, converti en chaîne `'latin1'` (un caractère = un octet : l'UTF-8 des accents, le BOM,
les octets bizarres traversent sans être interprétés), traité, réécrit par `Buffer.from(texte, 'latin1')`. Aucune
expression régulière à retour arrière sur le texte : un parcours caractère par caractère et `indexOf` pour les fermetures
de chaînes et commentaires longs (temps linéaire).

```js
/** @returns {{ ok: true, text: string, removed: number } | { ok: false, line: number, reason: string }} */
function strip(text) {}
/** Évènements dans l'ordre : { kind, start, end, line } ; kind : 'bom' | 'shebang' | 'ws' | 'eol' | 'comment' |
 *  'string' | 'long' | 'number' | 'name' | 'punct' ; ou { kind: 'error', line, reason } en dernier. */
function scan(text) {}
/** [ligne, écart, lexème] de chaque lexème hors blancs et commentaires ; écart = 1 si un blanc, une fin de ligne ou un
 *  commentaire le précède (ou s'il est le premier). */
function signature(text) {}
module.exports = { scan, strip, signature };
```

### 6.2 Lexeur (calqué sur `llex.c` de Lua 5.4)

Au début : un BOM UTF-8 (`EF BB BF`) est un évènement `bom` gardé tel quel ; puis si le caractère suivant est `#`, toute
la première ligne (sans sa fin) est un évènement `shebang` gardé tel quel (comme `luaL_loadfile`, qui la saute).

Ensuite, à la position `i` :

| Caractère(s) | Lexème | Règle |
|---|---|---|
| ` `, `\t`, `\f`, `\v` | `ws` | une suite de blancs |
| `\n`, `\r` | `eol` | `\r\n` et `\n\r` comptent pour **une** fin de ligne (deux octets), `\n` ou `\r` seul pour une ; `line++` |
| `--` suivi de `[`, de *n* `=` (n ≥ 0) et de `[` | `comment` long | jusqu'à la première occurrence exacte de `]` + *n* `=` + `]` (`indexOf` : équivalent au balayage de Lua, qui ne saute jamais de `]`) ; fins de ligne intérieures comptées ; absente → erreur « commentaire long non fermé » |
| `--` sinon | `comment` court | jusqu'à la fin de ligne exclue (`--[ x`, `--[=x`, `---[[` sont courts, comme dans Lua) ; fin de fichier permise |
| `-` seul | `punct` | |
| `"`, `'`, `` ` `` | `string` | jusqu'au même caractère non échappé. `\` : saute le caractère suivant ; si c'est une fin de ligne (`\r\n`, `\n\r` : les deux), `line++` ; après `\z`, saute aussi tous les blancs **et fins de ligne** qui suivent (comptées). Une fin de ligne brute non échappée, ou la fin du fichier → erreur « chaîne non fermée ». La contre-apostrophe est la chaîne de hachage de CfxLua : traitée comme une chaîne, au cas où. |
| `[` suivi de *n* `=` et de `[` | `long` | même fermeture que le commentaire long ; absente → erreur « chaîne longue non fermée » |
| `[` sinon | `punct` | (`[=` sans second `[` est une erreur pour Lua : le compilateur la verra, § 10) |
| chiffre, ou `.` suivi d'un chiffre | `number` | comme `read_numeral` : `0x`/`0X` → exposants `Pp`, sinon `Ee` ; boucle : exposant puis signe `+`/`-` facultatif, ou chiffre hexadécimal ou `.` ; puis une lettre collée est prise (Lua en fait une erreur). Ainsi `1e-5--c` donne `1e-5` puis un commentaire, `0x1p-4` un seul nombre. |
| lettre ASCII ou `_` | `name` | suivie de lettres, chiffres, `_` |
| tout autre octet | `punct` | un octet |

Les extensions de CfxLua autres que la contre-apostrophe (`/* */`, `+=`, `?.`…) ne sont **pas** reconnues : le dépôt est
du Lua 5.4 standard (luacheck et busted le lisent), et le compilateur de la preuve refuserait un fichier qui en
contiendrait (§ 10.1, § 14).

### 6.3 Ce que produit `strip`

Parcours des évènements avec un tampon `blancs` (les `ws` en attente) :

- `bom`, `shebang`, `string`, `long`, `number`, `name`, `punct` : écrire `blancs`, vider, écrire le lexème **tel
  quel**.
- `ws` : l'ajouter à `blancs`.
- `eol` : **jeter** `blancs` (blancs de fin de ligne retirés), écrire la fin de ligne telle quelle (`\n`, `\r\n`…).
- `comment` court : rien (les blancs d'avant restent en attente et tombent à la fin de ligne qui suit).
- `comment` long **sans** fin de ligne : si `blancs` est vide, il devient une espace (`a--[[c]]or b` → `a or b`, jamais
  `aor b`) ; sinon rien.
- `comment` long **avec** fins de ligne : jeter `blancs`, écrire ses seules fins de ligne, dans l'ordre et telles quelles
  (`\r\n` reste `\r\n`). Le code qui suit le commentaire sur sa dernière ligne reste sur cette ligne.
- `error` : rendre `{ ok: false, line, reason }` (le fichier sera laissé tel quel).
- Fin du fichier : jeter `blancs`.

Conséquences : chaque lexème garde **sa ligne** ; seules ses colonnes peuvent bouger (Lua n'en rapporte aucune) ; une
ligne qui n'était qu'un commentaire devient une ligne vide ; le contenu des chaînes (blancs de fin de ligne d'une chaîne
longue compris) n'est jamais touché ; l'indentation est gardée.

### 6.4 Ce qu'on ne fait pas

Ni renommage, ni retrait de l'indentation, ni fusion ou suppression de lignes (même vides, même en fin de fichier), ni
changement de fin de ligne, ni réécriture d'une chaîne ou d'un nombre, ni retrait des annotations `---@` autrement que
comme commentaires. La règle est « retirer ce que Lua ignore, garder chaque ligne à sa place ».

### 6.5 Contrôle à chaque fichier (dans `strip`, à chaque allègement)

Avant de rendre `ok`, `strip` vérifie que **`signature(entrée)` et `signature(sortie)` sont identiques** (même suite de
lexèmes, chacun à la même ligne, avec le même « écart ») **et** que les deux textes ont le même nombre de fins de ligne.
Sinon : `{ ok: false, line, reason: 'contrôle après allègement' }`. Ce contrôle attrape une fusion de lexèmes, un
lexème déplacé de ligne, une chaîne coupée ; il tourne aussi dans la Chancellerie, sans Lua (§ 7.1). La preuve
indépendante est celle du compilateur (§ 10.1).

## 7. Où se fait l'allègement

### 7.1 Chancellerie : installation et mises à jour (`installer.fetchSource`)

Un seul point, que `install` et `perform` traversent tous deux, **après l'extraction de l'archive et avant toute
empreinte** :

```js
async function fetchSource(updates, ref, job) {
  // … téléchargement et extraction inchangés …
  const root = dl.unwrap(dir);
  if (updates.leanLua !== false) leanSource(root, job);   // updates = settings() de la Chancellerie
  return root;
}
```

`leanSource(root, job)` (fonction locale d'`installer.js`) appelle `delivery.leanResources(layout(root).resources)`
dans un `try` ; une exception (défaut du code) est dite au journal de l'opération et **n'arrête rien** : chaque fichier
n'est réécrit qu'après son propre contrôle, l'arbre reste donc un mélange valide de fichiers allégés et intacts.

`delivery.leanResources(resources)` : pour chaque ressource, `servedLua(dir)` ; illisible → ressource laissée telle
quelle ; sinon `leanFile` sur chaque fichier `lean` (le manifeste en dernier). `leanFile(file)` : refuse au-delà de
**4 Mio** (« fichier trop gros ») ; lit, `strip`, réécrit seulement si le texte change ; rend `{ ok, before, after }` ou
`{ ok: false, line, reason }`. Résumé rendu : `{ resources, files, before, after, refused: [{ file, line, reason }],
skipped: [{ resource, reason }] }` (`file` = `ressource/chemin`).

Lignes du journal de l'opération (`job.say`, textes du panneau) :
- `Lua servi aux joueurs allégé de ses commentaires : 318 fichiers, 1 186 → 742 Ko.` (une fois) ;
- `Laissé avec ses commentaires (ligne 12 : chaîne non fermée) : vava_x/client/y.lua` (10 au plus, puis
  `… et N autres`) ;
- `Ressource vava_x laissée telle quelle : manifeste illisible pour l'allègement (forme illisible).` ;
- `updates.leanLua` à faux : `Allègement du Lua livré désactivé (updates.leanLua) : fichiers livrés avec leurs
  commentaires.`

Puis tout se passe comme avant, sur des fichiers allégés : `planResources` les empreinte, la fusion compare, la
sauvegarde et le retour arrière copient des dossiers entiers (§ 11.3). `staging/` est vidé comme avant.

### 7.2 Script du dépôt (`scripts/livraison.js`)

`node scripts/livraison.js <mode>`, lancé de n'importe où (racine = dossier parent de `scripts/`). Il charge
`../chancellerie/lib/delivery.js` (allègement, choix des fichiers) et `../chancellerie/lib/installer.js` pour sa seule
fonction `layout` (aucune écriture au chargement, comme `--verifier`). Codes de sortie : 0 succès, 1 écart ou refus,
2 usage.

| Mode | Fait | Sortie |
|---|---|---|
| `--liste` | `servedLua` sur chaque ressource du dépôt (`layout(racine)`) | une ligne par fichier Lua servi : `ressource<TAB>chemin<TAB>état` (`allégé`, `gardé (réglage)`, `gardé (files)`) ; pour un fichier de `vava_conseil_lua` : `ressource@conseil<TAB>chemin<TAB>allégé` (ou `gardé (réglage)` pour un `config.lua`) ; ressource illisible : `ressource<TAB>-<TAB>illisible : raison` et code 1 |
| `--essai <dossier>` | chaque fichier de `git ls-files -z -- '*.lua'` (copie de travail) est allégé dans `<dossier>/<chemin du dépôt>` | une ligne par fichier : `livre<TAB>chemin` (allégé à la livraison, paquet du Conseil compris), `depot<TAB>chemin` (jamais livré allégé, mais essayé quand même : tout le dépôt éprouve le lexeur), `refuse<TAB>chemin<TAB>ligne<TAB>raison` (lexeur) ; code 1 si un fichier `livre` est refusé |
| `--sortie <dossier>` | copie de livraison **disposée comme par l'installeur** : `<dossier>/[vava]/vAvA_core`, `<dossier>/[vava]/<module>`, `<dossier>/[vava-dev]/<exemple>` ; seuls les fichiers suivis par git (copie de travail), filtrés par le `skip` de `layout` ; puis `leanResources` sur les dossiers copiés (même fonction que la Chancellerie) | résumé (ressources, fichiers allégés, octets avant → après, refus) ; code 1 au moindre refus |

Garde-fous de `--essai` et `--sortie` : le dossier ne doit pas exister ou être vide ; son chemin réel (`realpath` du plus
proche parent existant, puis le reste) ne doit **ni être dans le dépôt ni le contenir** ; les dossiers sont créés par le
script (aucune jonction suivie). Raison : sur le serveur de test, `resources\[vava]\<nom>` sont des jonctions vers la
copie git ; écrire au travers allégerait le dépôt lui-même.

## 10. Preuve et vérification

### 10.1 Le compilateur comme juge (`scripts/lib/meme-code.lua`)

Indépendant du lexeur JavaScript : c'est **Lua 5.4** qui lit les deux textes.

```lua
--- Même code, mêmes lignes ? `nil, raison` si l'original ne se compile pas ; `false, raison` si l'allégé diffère.
---@return boolean|nil same, string? reason
function M.compare(original, allege, chemin) end
```

- Préparation des deux textes comme `luaL_loadfile` : BOM UTF-8 de tête retiré, première ligne commençant par `#`
  vidée (sa fin de ligne gardée).
- `f1 = load(original, '@' .. chemin, 't')` ; échec → `nil, 'original illisible : ' .. err`.
- `f2 = load(allege, '@' .. chemin, 't')` ; échec → `false, 'allégé illisible : ' .. err`.
- `string.dump(f1) == string.dump(f2)` (**sans** `strip` : les numéros de ligne de chaque instruction, les lignes de
  définition des fonctions, les noms des variables locales sont dans la comparaison) → `true`.
- Sinon : `string.dump(f1, true) == string.dump(f2, true)` → `false, 'numéros de ligne différents'` ; sinon `false,
  'code différent'`.

Angle mort théorique (deux textes différents compilés à l'identique, par exemple `1 + 2` et `3`) sans objet : l'allègement
ne fait que retirer des commentaires et des blancs ; une erreur du lexeur coupe une chaîne, colle deux lexèmes ou mange
du code, ce qui change toujours la fonction compilée ou la rend illisible.

Ligne de commande (`lua scripts/lib/meme-code.lua <dossier>`, depuis la racine du dépôt ; module si chargé sans
argument, `return M`) : lit sur l'entrée la sortie de `livraison.js --essai`, compare chaque `chemin` du dépôt à
`<dossier>/<chemin>` (fichiers ouverts en `'rb'`), écrit `ÉCART chemin : raison` à chaque écart, puis
`MÊME CODE : OK (612 fichiers prouvés, dont 318 livrés ; 2 non compilables hors livraison : …)`. Règles :

| Ligne | Original compilable | Original non compilable |
|---|---|---|
| `livre` | doit être identique, sinon ÉCART (échec) | ÉCART (échec : on ne livre pas ce qu'on ne peut prouver) |
| `depot` | doit être identique, sinon ÉCART (échec : le lexeur se trompe, même sur un fichier non livré) | noté « non compilable hors livraison », sans échec (cas d'essai de l'audit) |
| `refuse` | ÉCART « le lexeur refuse un fichier que Lua lit » (échec) | sans échec (accord avec Lua) |

Code 1 au moindre ÉCART. Aucune dépendance : `io`, `load`, `string.dump`. Sous Windows sans `lua` (poste du porteur),
l'agent le lance par la même voie que les essais busted (lupa), et le note au rapport.

### 10.2 Ce que la preuve couvre

- **Tout le dépôt** (`git ls-files '*.lua'`, ≈ 600 fichiers : modules, core, exemples, essais, contenu du Codex et ses
  chaînes longues `[==[…]==]`), pas seulement le Lua livré : le lexeur est éprouvé sur tout ce que le projet écrit.
- `tests/livraison/cas_difficiles.lua` (§ 12.2), suivi par git, donc compris.
- Les fins de ligne de la copie de travail (CRLF sous Windows, LF en CI) : les deux sont éprouvées selon la machine.

### 10.3 Étape de `scripts/verifier.sh`

Après « Essais de pages », avant « Audit réseau et sécurité » :

```bash
titre "Lua livré sans commentaires (T-154)"
# allègement de chaque fichier Lua suivi par git par le lexeur de la Chancellerie, prouvé par le compilateur Lua 5.4
# (scripts/lib/meme-code.lua) ; liste des fichiers allégés recoupée avec scripts/lib/manifeste.awk ; essais du lexeur.
# node absent : rien n'est lancé (échec en CI) ; lua absent : échec (comme busted)
LUA=$(command -v lua5.4 || command -v lua || true)
if ! command -v node >/dev/null; then
    echo "node absent : livraison non essayée"; [[ -n "${CI:-}" ]] && echec=1
elif [[ -z "$LUA" ]]; then
    echo "lua absent : preuve de la livraison non lancée"; echec=1
else
    tmp=$(mktemp -d)
    node tests/livraison/essais.js || echec=1
    node scripts/livraison.js --essai "$tmp/allege" > "$tmp/liste.txt" || echec=1
    "$LUA" scripts/lib/meme-code.lua "$tmp/allege" < "$tmp/liste.txt" || echec=1
    node scripts/livraison.js --liste | cut -f1,2 | sort -u > "$tmp/js.txt" || echec=1
    ./scripts/poids-client.sh --liste | grep -i '\.lua$' | sort -u > "$tmp/awk.txt"
    if ! diff -u "$tmp/awk.txt" "$tmp/js.txt"; then
        echo "ÉCART : la livraison (chancellerie/lib/delivery.js) et scripts/lib/manifeste.awk ne voient pas les mêmes fichiers Lua servis"
        echec=1
    fi
    rm -rf "$tmp"
fi
```

`poids-client.sh --liste` : une ligne `ressource<TAB>chemin` par fichier servi (même boucle, même lecteur, sans
`taille`), `fxmanifest.lua` compris, puis une ligne `ressource@conseil<TAB>chemin` par fichier du côté `conseil` de
`manifeste.awk` (§ 5.4 ; jokers développés de même). Les deux listes comparées portent donc aussi le Lua du paquet du
Conseil : un fichier de `vava_conseil_lua` oublié par l'un des deux lecteurs est un écart. Les en-têtes de `poids-client.sh` (« informatif ») et de `verifier.sh` (liste des
étapes) sont mis à jour.

## 11. Effets

### 11.1 Audit (`audit-reseau.sh`), plafond de `vava_loading`, T-153

Aucun changement : l'audit lit le **dépôt** (commenté) ; ses règles ignorent déjà les commentaires. Le plafond de

### 11.2 Débogage

- Une erreur en jeu (`F8`, console serveur) `@vava_x/client/y.lua:123` désigne **la même ligne** que le dépôt au commit
  installé (`data/install.json` → `source`) : ligne 123 du fichier livré = même instruction, sans ses commentaires ;
  ouvrir le dépôt à ce commit pour les lire. Prouvé par le compilateur (lignes des instructions dans `string.dump`).
- Le Lua du seul serveur et les réglages gardent leurs commentaires sur le disque de l'exploitant.
- Le serveur de développement (copie git) reste commenté.
- `README.md` § Installation, une ligne : « Débogage : les fichiers livrés gardent leurs numéros de ligne ; leurs
  commentaires sont dans le dépôt, au commit installé. »

### 11.3 Chancellerie : empreintes, mises à jour, retour arrière

- **Empreintes** : celles des fichiers allégés (§ 8). Une version qui ne change que des commentaires de fichiers livrés
  donne les mêmes empreintes : rien à copier pour eux.
- **Première mise à jour allégée** : la Chancellerie qui l'applique est celle déjà installée ; la mise à jour qui
  **apporte** la 1.9.0 est donc préparée par l'ancienne (Lua encore commenté) ; c'est la **suivante** qui allège. Alors,
  pour chaque fichier livré : disque = empreinte installée (commentée) ≠ nouvelle (allégée) → copié ; toutes les
  ressources à script client sont « mises à jour » une fois, et chaque joueur retélécharge une fois leur Lua (allégé).
  Un fichier livré que l'exploitant avait modifié sur place est remplacé et le sien gardé à côté en `.local` (message
  habituel « Fichiers modifiés remplacés ; ancienne version gardée à côté ») — même pour un fichier qui n'a pas changé en
  amont (§ 16-10). Les réglages, jamais allégés, ne bougent pas : `.nouveau` comme avant.
- **Installation à la main, puis première mise à jour** (version inconnue) : un fichier livré diffère → remplacé (règle
  existante pour les fichiers qui ne sont pas des réglages).
- **Retour arrière** : inchangé (copie de dossiers entiers avant écriture, restaurés à l'identique, `install.json`
  compris).
- **Chancellerie remise à l'ancienne** (`demarrer.bat` / `.sh`) ou **`leanLua` à faux** : à la mise à jour suivante, les
  fichiers livrés (allégés sur le disque, empreintes allégées) sont remplacés par leurs versions commentées : aucun
  conflit, un retéléchargement.
- **Copie git** : toujours refusée (`inGitCheckout`) ; la règle n'est pas touchée.
- **`--verifier`** : `luastrip.js` et `delivery.js` se chargent sans rien lancer ni écrire (ils n'exportent que des
  fonctions) : une Chancellerie 1.9.0 passe son contrôle avant d'être installée.

Inchangés : ils lisent le dépôt. Aucun essai existant n'est modifié ni affaibli.

### 11.5 T-157 (code de l'Atelier livré au seul Conseil) : compatible, dans les deux ordres

- **Ce que T-154 fait pour T-157** : les fichiers de `vava_conseil_lua` (dont `config_conseil.lua`) sont allégés sur le
  disque comme le Lua livré (§ 5.1, règle 3). Le serveur de T-157 les lit par `LoadResourceFile` sur la copie déployée
  (§ 7.1 de T-157) : le paquet est allégé sans rien changer à T-157 (≈ 92 Ko de Lua estimés par T-157, dont une bonne

- **Numéros de ligne** : chaque fichier du paquet garde ses lignes (§ 6.3) ; T-157 ramène `\r\n` à `\n`, ce qui ne
  change pas les lignes ; `load(code, '@@vava_atelier/client/placer.lua', 't', env)` rapporte donc la ligne du fichier
  d'origine dans le dépôt.
- **Empreinte** : T-157 la calcule au démarrage sur le texte déployé (allégé ou non) : une version qui ne change que des
  commentaires du paquet donne la même empreinte, et aucun membre ne retélécharge le paquet.
- **Double contrôle** : la compilation de contrôle de T-157 au démarrage (§ 7.1 de T-157, `load` sans exécution)

- **Ordre des tâches** :
  - T-154 avant T-157 : `delivery.js` connaît déjà `vava_conseil_lua` et `manifeste.awk` le suit (§ 5.4) ; aucun
    manifeste ne l'utilise encore ; les essais de `servedLua` (§ 12.1) le couvrent. T-157 n'a plus à modifier la partie

  - T-157 avant T-154 : `manifeste.awk` suit déjà les directives (on ne la refait pas) ; `--liste` et le recoupement
    voient aussitôt les neuf fichiers de `vava_atelier@conseil` ; la mesure avant et après (§ 10.4) compte le paquet à
    part (ligne `vava_atelier@conseil` de T-157).
- `vava_conseil_web` (≈ 152 Ko de page dans le paquet) n'est pas allégé : c'est la tâche web du § 15.

## 14. Risques, et comment la spec les ferme

| Risque | Fermeture |
|---|---|
| Un fichier livré cassé par une erreur du lexeur | preuve par **le compilateur Lua** sur tout le dépôt à chaque vérification (§ 10) ; contrôle par signature à chaque allègement, y compris dans la Chancellerie (§ 6.5) ; tout fichier illisible ou au contrôle raté est **laissé tel quel** (le commenté est valide) ; essais des cas difficiles ; essai en jeu de la copie entière (§ 13) |
| Numéros de ligne faux en jeu | fins de ligne gardées une à une ; les lignes de chaque instruction sont dans la comparaison `string.dump` (sans `strip`) ; essai 13-10 |
| Lexeur de la Chancellerie installée plus ancien que le Lua téléchargé | la grammaire lexicale de Lua 5.4 est fixe et entièrement suivie (§ 6.2) ; le dépôt reste du Lua 5.4 standard (luacheck, busted, preuve) ; contrôle et repli par fichier ; `updates.leanLua` pour couper |
| Extension de CfxLua (`/* */` qui contiendrait `--`) | non reconnue ; le compilateur standard de la preuve et luacheck refusent le fichier dans le dépôt avant toute livraison |
| Lecteur de manifeste JavaScript qui diverge de `manifeste.awk` | recoupement des deux listes à chaque vérification (§ 10.3) ; forme illisible → ressource entière laissée telle quelle |
| L'exploitant perd le mode d'emploi de ses réglages, ou les `-- PLACEHOLDER` | réglages jamais allégés (§ 5.2) ; `.nouveau` inchangé |
| Le script allège la copie git au travers d'une jonction | `--essai` et `--sortie` n'écrivent que dans un dossier neuf ou vide, hors du dépôt (chemin réel) ; jamais dans le dépôt |
| Fusion de l'installeur perturbée | aucun changement de `plan()` ; empreintes de ce qui est sur le disque ; essais de fusion (§ 12.1) ; une seule transition, connue et dite (§ 11.3) |
| Retour arrière incomplet | inchangé (dossiers entiers) |
| Entrée hostile (archive piégée) | rien de nouveau n'est exécuté : le lexeur ne fait que lire ; temps linéaire, `indexOf`, 4 Mio par fichier au plus ; le dépôt téléchargé est déjà du code de confiance (il tourne sur le serveur) |
| Nouvelle dépendance | aucune : node et Lua 5.4 déjà requis (Chancellerie, busted), `assert` intégré à node |
| Surcharge réseau | aucun envoi nouveau ; − 400 Ko par nouveau joueur ; plus de retéléchargement pour un commentaire |
| Vérification sans node (poste sans node) | message, et échec en CI (`CI` posé par GitHub) ; node est déjà là pour les essais de pages et la Chancellerie |

1. **Où alléger.** (a) Un script de livraison seulement (copie à produire à la main) ; (b) la Chancellerie seulement ;

   script. *Recommandation : (c)* — tout serveur tenu par la Chancellerie en profite sans rien faire ; le script sert à
   la preuve, à la mesure, à l'essai en jeu et aux hébergeurs sans Chancellerie ; un seul lexeur à prouver.
2. **Serveur de test du porteur.** (a) Inchangé (copie git commentée) ; (b) une copie allégée refaite après chaque
   `git pull` et des jonctions vers elle ; (c) alléger sur place. *Recommandation : (a)* — réseau local sans coût, confort

   dépôt.
3. **Quoi.** (a) Le Lua servi d'après les manifestes, manifeste compris ; (b) tout le Lua ; (c) le Lua servi sans les
   manifestes. *Recommandation : (a)* — seul ce qui est téléchargé coûte ; le Lua du serveur garde ses commentaires
   pour l'exploitant ; le manifeste est servi à chaque joueur et se prouve comme le reste.
4. **Réglages (`config_client.lua`, `config/shared.lua`).** (a) Jamais allégés ; (b) allégés comme le reste ; (c)

   (≈ 15 Ko compressés) gardés, mais le mode d'emploi de l'exploitant, les `-- PLACEHOLDER` et la lecture de
   `.nouveau` restent intacts, et la fusion ne change pas ; (c) ajoute un fichier à suivre par fichier de réglages.
5. **Langage.** (a) JavaScript dans `chancellerie/lib/`, jugé par le compilateur Lua ; (b) Lua (la Chancellerie ne
   peut pas l'exécuter) plus une copie en JavaScript ; (c) `awk`/`bash` (absents d'une Chancellerie sous Windows).
   *Recommandation : (a)*.
6. **Preuve.** (a) Compilateur Lua 5.4 (`string.dump` avec lignes) sur tout le dépôt, plus signature à chaque
   allègement ; (b) seulement une relecture des jetons par le même lexeur. *Recommandation : (a)* — (b) ne voit pas une
   erreur de classement du lexeur (elle se reproduit des deux côtés).
7. **Blancs.** (a) Commentaires et blancs de fin de ligne seulement ; (b) plus l'indentation ; (c) minification.
