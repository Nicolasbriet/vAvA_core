## 1. But joueur

Une épée à la main, on lève la garde en maintenant **R** : les coups de face sont amortis, bien mieux derrière un
bouclier, jusqu'à ce que la garde cède sous les coups. Un appui bref sur **R** au bon moment **pare** : la lame adverse
est détournée et l'attaquant chancelle, ouvert à la riposte. **Espace** fait un pas de côté qui laisse passer le coup.

Piliers du lore : « Personne ne sait tout faire » et « le mage a besoin d'un garde » (le porteur de bouclier protège, le
bouclier se fabrique chez le menuisier et s'use à chaque coup arrêté, il retourne chez l'artisan) ; « Les objets portent
des histoires » (l'arme qui pare et le bouclier qui bloque s'usent) ; le combat reste une affaire de lecture et de rythme
**entre joueurs** : la défense récompense celui qui lit son adversaire, jamais un calcul du client.

## 2. Périmètre

### 2.1 Dedans

- **Trois techniques défensives en données** au format de `COMBAT_V1.md` § 3, style `epee_une_main` : Garde (`blocage`),
  Parade (`parade`), Pas de côté (`esquive`) ; contrôle du format **selon le type** (§ 5.1) ; touches de défense dans
  `styles.<style>.keys`.
- **Le RPC existant `vava_combat:use`** accepte les types défensifs (même schéma, même débit, même réservation) ; un
  **nouveau RPC `vava_combat:lower`** (sans argument) abaisse la garde. Rien d'autre côté client → serveur.
- **Fenêtres tenues par le serveur**, en mémoire, **sans minuterie** : parade (`[openAt, closeAt]`), invulnérabilité
  d'esquive (idem), garde levée (de `openAt` jusqu'à l'abaissement, tenue minimale `active`).
- **Trois modificateurs** au registre `vava_health:modifiers` (étapes `esquive`, `parade`, `blocage`), purs : ils lisent
  la mémoire du module et les positions lues par le serveur, rendent un résultat, notent leur décision.
- **Suites d'une défense** (hook `vava_health:hit` `after`) : attaquant paré qui chancelle et dont le coup est annulé ;
  compteur de garde et **garde brisée** ; usure de l'arme qui pare ou du bouclier (ou de l'arme) qui bloque ; hook
  `vava_combat:defended`.
- **Délais anti-abus** : parade ratée → aucune autre parade avant 600 ms ; deux pas de côté espacés de 1,5 s ; garde
  brisée → ni garde ni parade pendant 1,2 s.
- **Issues** envoyées par l'évènement existant `vava_combat:hit` : `parry` (attaquant chancelant), `block`, `break`
  (garde brisée, défenseur chancelant) ; `dodge` reste silencieux (R-3) mais nommé. **Aucun évènement nouveau.**
- **Branchement de l'endurance** sans la faire (§ 7.8) : coûts écrits en données (`stamina`), une interface interne
  `defense.spend` que T-114 remplacera, et un **compteur provisoire** de garde brisée.
- **Client** : touche R (appui : parade ; maintenu : garde), Espace (esquive, mode combat actif seulement), gestes
  `-- PLACEHOLDER`, garde abaissée quand on la relâche, perd le mode ou chancelle ; réactions `parry` et `break`.
- Tests unitaires, procédure en jeu `docs/tests/combat.md` § 4 « Défense », README, `docs/api.md`, `COMBAT_V1.md`.

### 4.2 `config.lua` (serveur seul)

```lua

    missCooldownMs = 600,      -- parade ratée (aucun coup paré dans sa fenêtre) : aucune autre parade avant fin de fenêtre + ce délai

config.defense.dodge = {
    cooldownMs = 1500,         -- entre le départ de deux pas de côté (≤ 17 % du temps invulnérable)
    tags = { 'melee', 'ranged' },                         -- évités : au moins une de ces étiquettes
    never = { 'undodgeable', 'area', 'overTime', 'native', 'reflected' }, -- jamais évités

config.defense.block = {
    tags = { 'melee' },        -- bloqués : coups portant une de ces étiquettes (les sorts : hors v1)
    shieldArcBonus = 40,       -- degrés ajoutés à l'arc protégé quand le bouclier est au bras (120 → 160)

config.defense.parryTags = { 'melee' } -- parés : coups `parryable` portant une de ces étiquettes
-- Garde brisée PROVISOIRE (remplacée par l'endurance de T-114) : points ajoutés par coup bloqué, garde brisée à `points`
-- (au bouclier : `shieldPoints`), compte remis à zéro après `resetMs` sans coup bloqué (lever et baisser la garde ne le
-- remet pas à zéro).
config.defense.guardBreak = { points = 4, shieldPoints = 6, heavyWeight = 2, resetMs = 3000 }
config.defense.modifierPriority = 50   -- priorité des trois modificateurs dans leur étape (0 à 99)
config.defense.memoMax = 64            -- décisions en attente de leur suite (une par coup en cours de chaîne)
config.defense.memoMs = 1000           -- une décision plus vieille est oubliée (coup tombé en erreur avant sa suite)

-- Issues jamais envoyées aux proches (personne ne les montre en 1.3.0 ; T-155 pourra changer cette liste).
config.reactions.silent = { 'dodge', 'absorb' }
```

| `swings[src]` (existant) | un geste défensif accepté est un `swing` comme un coup : `{ seq, id, def, startedAt, openAt, closeAt, endAt, chainCount, instanceId, item, characterId, cancelled, pending, refused, prev }` ; **garde ouverte** : `closeAt = nil`, `endAt = nil` ; + `parried` (parade qui a paré), `lowerRequested` (abaissement demandé pendant la réservation), `guard` (cache § 7.3) | inchangé (déchargement, départ, arrêt) |

| `defense.lastParry[src]` | dernière parade acceptée (son `closeAt`, `parried`) | idem |
| `defense.lastDodge[src]` | départ du dernier pas de côté accepté | idem |
| `defense.points[src]` | `{ value, at }` compteur provisoire de garde (§ 7.8) | idem, et garde brisée |
| `defense.brokenUntil[src]` | fin de la garde brisée | idem |
| `defense.memo[hitId]` | décision d'un modificateur en attente de sa suite : `{ at, kind, target, source, swing, weight }` ; ≤ `memoMax` entrées | retirée par la suite (même tour) ; purgée au-delà de `memoMs` |

Bornées par le nombre de joueurs (et `memoMax` pour les coups). **Aucune minuterie** : une fenêtre défensive est une
paire d'instants comparée à l'horloge quand un coup arrive.

## 7. Vérifications serveur

### 7.1 `swings.use` : types défensifs (`server/swings.lua`)

Refus **en mémoire d'abord**, dans cet ordre (inchangé sauf les lignes marquées) :

| # | Vérification | Refus |
|---|---|---|
| 1 | `VavaCombat.ready` | `not_ready` |
| 2 | technique connue | `unknown_technique` |
| 3 | **`def.type` ∈ `USABLE_TYPES`** (`legere`, `lourde`, `blocage`, `parade`, `esquive`) | `not_attack` (type `garde`) |
| 4 | chancellement en cours | `staggered`, attente |
| 5 | dégainer en cours | `drawing`, attente |
| 6 | **nouveau** : `blocage` ou `parade` et `defense.brokenUntil[src] > now` | `guard_broken`, attente |
| 7 | **nouveau** : `parade` et `defense.parryWait(lastParry[src], now, cfg)` > 0 | `parry_cooldown`, attente |
| 8 | **nouveau** : `esquive` et `defense.dodgeWait(lastDodge[src], now, cfg)` > 0 | `dodge_cooldown`, attente |
| 9 | admission `techniques.admit(prev, def, id, now, rules)` ; **coup d'avant = garde ouverte → `guarding`** (sans attente) | `guarding` / `busy` / `not_opener` / `chain_limit` |
| 10 | réservation `pending` posée (T-112 S-2), puis `confirm` sous `pcall` | — |

`confirm` (inchangé pour les attaques) : personnage, arme **réellement tenue** du catalogue (pas un bouclier), style de
l'arme, technique de ce style, pas à terre, pas en véhicule, contrôle dur de la magie, crochet `vava_combat:using`
(charge **+ `kind = def.type`**), position lue. Pour un geste défensif : pas d'arc ni de cible (`target = 0`) ; **en
plus**, pour `blocage`, le cache de garde (§ 7.3), qui peut lire une fois la pile du bouclier (`bridge.Items`).

Acceptation (après `confirm`) :
- attaque : inchangé (deux minuteries) ; puis `defense.onAccepted(src, swing)` → `defense.active[src] = nil` (une
  attaque ferme toute fenêtre défensive encore ouverte, au plus `earlyMs` après son admission en chaîne) ;
- défense : **aucune minuterie** ; `defense.onAccepted(src, swing, now)` → `defense.active[src] = swing` ; parade :
  `lastParry[src] = swing` ; esquive : `lastDodge[src] = swing.startedAt` ; blocage : si `swing.lowerRequested`, la
  garde est fermée aussitôt (§ 7.4). Réponse `true`.

`swings.cancel(src, raison)` (C-3, inchangé) **ferme en plus** toute garde ouverte qu'il marque : `closeAt = max(now,
openAt + active)`, `endAt = closeAt + recovery` (même règle que l'abaissement : une garde annulée garde son cycle, S-1).
Raisons ajoutées : `parried` (l'attaquant a été paré), `broken` (garde brisée). `CANCEL_CODES` : `parried → staggered`,
`broken → guard_broken` (attente lue dans `reactions.staggeredLeft` ou `brokenUntil`).

### 7.2 Règles pures (`shared/defense.lua`, serveur seul)

Aucune native, aucun état ; jamais d'erreur sur une valeur non finie (rendent `false`/`nil`).

- `defense.open(swing, now)` → vrai si `swing` existe, n'est ni `pending`, ni `refused`, ni `cancelled`, et :
  `parade`, `esquive` : `openAt ≤ now ≤ closeAt` ; `blocage` : `openAt ≤ now` et (`closeAt == nil` ou `now ≤ closeAt`).
- `defense.close(swing, now)` → pose `closeAt = max(now, openAt + active)`, `endAt = closeAt + recovery` sur une garde
  ouverte ; rien sinon (rend vrai si elle a fermé).
- `defense.frontal(defPos, defHeading, atkPos, angleDeg, cfg)` → vrai si `geometry.flat` < `geometry.closeRange` (corps
  au contact, comme pour les attaques) ou si `geometry.flatAngle(forward(defHeading), defPos, atkPos) ≤ angleDeg / 2 +
  tolerance.angle` ; hauteur : `|dz| ≤ geometry.maxHeight + tolerance.height`.
- `defense.tagsMatch(tags, any, never)` → vrai si une étiquette de `any` est posée et aucune de `never`.
- `defense.blockFactor(guard, hungInstanceId, wearCfg)` → part bloquée : bouclier au bras **encore accroché** (même
  numéro de pile qu'au cache) → `shieldBlock` (× `wear.dullFactor` s'il est émoussé), sinon `weaponBlock` (× `dullFactor`
  si l'arme est émoussée) ; rend aussi `'shield'` ou `'weapon'`.
- `defense.blockedAmount(amount, factor)` → `min(amount, tenth(amount × factor))`.
- `defense.parryWait(last, now, cfg)` → `nil` si aucune parade, si elle a paré (`parried`), sinon
  `max(0, last.closeAt + missCooldownMs − now)` (nil si 0). Une parade annulée (chancelée) compte comme ratée.
- `defense.dodgeWait(lastStart, now, cfg)` → `lastStart + dodge.cooldownMs − now` si positif, sinon nil.
- `defense.addPoints(state, weight, now, cfg, shield)` → `newState, broken` : remis à 0 si `now − state.at ≥ resetMs` ;
  `value + weight` ; `broken` si `value ≥ (shield and shieldPoints or points)` (compteur provisoire, § 7.8).
- `defense.weightOf(techniqueDef)` → `heavyWeight` si `type == 'lourde'`, sinon 1 (technique inconnue : 1).

### 7.3 Cache de la garde (au `confirm` d'un `blocage`)

`swing.guard = { weaponBlock, weaponDull, shieldInstanceId?, shieldItem?, shieldBlock?, shieldDull?, arc }`, lu une fois :
- arme : fiche (`catalog.weapon(held.item).block`), émoussée par `weapons.durabilityOf(held.metadata, def).dull` (pile
  déjà lue par `confirm`) ;
- bouclier : `VavaCombat.shields.hungOf(src)` (mémoire) **et** `shield.position(held.item, cfg.weaponClasses,
  cfg.shield.armWith, cfg.shield.armWithEmptyHand) == shield.ARM` ; si oui, une lecture `bridge.Items(src, item)` pour
  sa solidité (`durabilityOf`) ; inventaire muet ou pile absente : pas de bouclier ;
- `arc = def.hit.angle + (bouclier and config.defense.block.shieldArcBonus or 0)` (plafonné à 180).

Le cache reste juste : changer de main annule la garde (hook `hold`, T-112) ; un bouclier décroché change
`hungOf(src).instanceId` (relu en mémoire à chaque coup) ; une usure qui émousse pendant la garde met le cache à jour
(§ 7.5). **Jamais** l'export `shield(src)` ni `shields.view` dans un modificateur.

### 7.4 Abaisser la garde : `defense.lowerRpc(src)` (`server/defense.lua`)

Ne cède jamais la main. `swing = swings.of(src)` :
- `swing` est un `blocage` **accepté** à garde ouverte → `defense.close(swing, now)` ; `true` ;
- `swing` est un `blocage` **réservé** (`pending`) → `swing.lowerRequested = true` ; `true` (fermée à l'acceptation) ;
- sinon `false, 'no_guard'`.

La garde reste effective jusqu'à son `closeAt` (tenue minimale `active` : un appui éclair ne lève pas une garde gratuite
de 0 ms ni ne la retire avant d'avoir servi). Pendant `recovery`, aucune technique ne part (admission `busy`), sauf une
technique de `garde_epee.chain` (vide par défaut).

### 7.5 Les trois modificateurs (`server/defense.lua`)

Déclarés par `bridge.DeclareModifiers` au `setup` si le registre existe, et de nouveau sur `core:module:ready` quand
`name == 'vava_health'` (le registre disparaît avec lui) ; chaque ajout isolé, une erreur = une ligne de console.

| Clé | Étape | Priorité | `kinds` | Libellé |
|---|---|---|---|---|
| `vava_combat:esquive` | `esquive` | `modifierPriority` | — (tous : les projectiles de sorts compris) | `Pas de côté` |
| `vava_combat:parade` | `parade` | idem | `config.kinds` (tranchant, contondant, percant) | `Parade` |
| `vava_combat:blocage` | `blocage` | idem | idem | `Garde` |

Contrat respecté : aucun ne cède la main, aucun ne lance `hit`, aucun ne change l'état du jeu ; chacun **rend** un
résultat et, s'il agit, **note** sa décision dans `defense.memo[ctx.id]` (mémoire du module). Commun aux trois, en
tête, dans cet ordre (sortie `nil` au premier échec) :
1. `swing = defense.active[ctx.target]` existe, du bon type, et `defense.open(swing, now)` ;
2. `swing.characterId == ctx.targetCharacter` (même personnage) ;
3. `not bridge.InVehicle(ctx.target)`.

Puis :
- **Esquive** : `defense.tagsMatch(ctx.tags, dodge.tags, dodge.never)` → `{ cancel = 'esquive' }`, mémo `{ kind =
  'dodge' }`. Aucune exigence sur la source (un projectile de sort lancé par un joueur est évité aussi ; un coup sans
  source, la faim, une zone ne le sont jamais : `area`, `overTime`, `native` dans `never`, et `kinds` du monde jamais
  étiquetés `melee` ni `ranged`).
- **Parade** : `ctx.tags.parryable`, `tagsMatch(ctx.tags, parryTags, {})`, `ctx.source` entier ≠ `ctx.target`,
  positions et cap lus (`bridge.Position(target)`, `bridge.Position(source)`, `bridge.Heading(target)`) et
  `defense.frontal(…, swing.def.hit.angle, cfg)` → `{ cancel = 'parade' }`, mémo `{ kind = 'parry', source, swing }`.
- **Blocage** : `not ctx.tags.unblockable`, `tagsMatch(ctx.tags, block.tags, {})`, `ctx.source` entier ≠ cible,
  `defense.frontal(…, swing.guard.arc, cfg)` ; `factor, by = defense.blockFactor(swing.guard, hungOf(target)?.instanceId,
  cfg.wear)` ; `blocked = defense.blockedAmount(ctx.amount, factor)` ; `blocked > 0` → `{ blocked = blocked }`, mémo `{
  kind = 'block', source, swing, by, weight = defense.weightOf(catalog.technique(ctx.technique)) }`.

Mémo pleine (`memoMax`) : purge des entrées plus vieilles que `memoMs` ; toujours pleine → le modificateur rend `nil`
(aucune défense pour ce coup, une ligne de console par minute). Cela ne se produit pas en jeu (la suite retire la
décision dans le même tour).

Exemples (Épée courte qualité 50, Taille × 1,0 = 12) : garde à l'épée (0,40) → 4,8 bloqués, 7,2 appliqués ; au Bouclier
rond (0,70) → 8,4 bloqués, 3,6 appliqués ; bouclier émoussé (0,35) → 4,2 bloqués. Fendant (21,6) au bouclier → 15,1
bloqués, 6,5 appliqués.

Un coup **non parable** (le Fendant) pendant une fenêtre de **parade** n'est ni paré ni bloqué : il porte et fait
chanceler (on le bloque ou on l'esquive). Un coup de dos pendant la garde porte entièrement ; la garde reste levée (sauf
chancellement d'un Fendant, qui l'annule).

### 7.6 Suites d'une défense : hook `vava_health:hit` `after` (`defense.onHitAfter`)

Abonné une fois au `setup` par `bridge.OnHitAfter` (le hook appartient au core : l'abonnement survit aux redémarrages de
`vava_health`). Pour **chaque** coup du jeu : `memo = defense.memo[payload.id]` ; absent → retour (une lecture de
table). Sinon la décision est retirée de la mémo, puis :

| Décision | Suite (mémoire seulement, aucune attente) |
|---|---|
| `dodge` | `bridge.RunAfter(HOOKS.DEFENDED, { source = cible, characterId, outcome = 'dodge', technique = swing.id, attacker = source?, hitId })` ; rien d'autre |
| `parry` | `swing.parried = true` ; `swings.cancel(source, 'parried')` (le coup paré et sa suite déjà réservée : C-3) ; `reactions.stagger(source, cfg.stagger.durationMs, now, true)` (§ 7.7) ; usure **différée** de l'arme de la parade (`swing.instanceId`, `swing.item`) ; issue imposée `outcomes[id] = 'parry'` si `payload.origin == ressource` ; hook `defended` (`outcome = 'parry'`) |
| `block` | si `payload.downed` : rien d'autre (la mise à terre l'emporte). Sinon `ok, broken = defense.spend(cible, 'block', { technique = swing.def, weight = memo.weight, shield = memo.by == 'shield', now })` (§ 7.8 ; en 1.3.0 : `defense.addPoints` sur `points[cible]`) ; usure différée du bouclier (`by == 'shield'`, pile `swing.guard.shieldInstanceId`) ou de l'arme ; si `broken` : `swings.cancel(cible, 'broken')` (garde fermée), `brokenUntil[cible] = now + guardBrokenMs`, `points[cible] = nil`, `reactions.stagger(cible, guardBrokenMs, now, true)`, issue `'break'` ; sinon issue `'block'` ; hook `defended` (`outcome = 'block'` ou `'break'`) |

**Usure différée** : `SetTimeout(0, function() wear.apply(cible, instanceId, item, catalog.weapon(item), characterId)
end)` — hors de la chaîne et de son chronomètre ; `wear.apply` relit la pile avant d'écrire (une écriture au plus par
coup défendu). Si le pas d'usure émousse la pièce et que `defense.active[cible]` est encore cette garde, le cache est mis
à jour (`weaponDull` ou `shieldDull`). Règles d'usure inchangées (chance d'épargner 40 % × qualité, seuils prévenus au
seul porteur).

L'attaquant, lui, use toujours son arme par `strike.run` (`wear.cancelledStages` contient déjà `parade` et `blocage`) ;
jamais sur une esquive.

### 7.7 Chancellement et issues (`server/reactions.lua`)

- `reactions.stagger(src, ms, now, force)` : `force` (interne) ignore l'immunité en cours, mais la **renouvelle**
  (`immuneUntil = now + ms + staggerImmunityMs`). Utilisé par la parade (l'attaquant chancelle 0,9 s : c'est lui qui a
  frappé dans une parade) et la garde brisée (1,2 s : gagnée par des coups répétés). Le Fendant reste sans `force` (règle
  d'équité de T-112). Conséquence voulue : après un chancellement forcé, aucun Fendant ne refait chanceler avant 3 s.
- `reactions.after(swing, cible, result)` : issue = `'down'` si `result.downed` ; sinon `defense.takeOutcome(result.id)`
  s'il y en a une (`parry`, `block`, `break`) ; sinon `weapons.outcome(result)` (inchangé). Un blocage partiel
  (`applied > 0`) est donc envoyé `block`, pas `hit` (étincelles, pas de sang, pas de tressaillement) ; le Fendant
  bloqué ne fait pas chanceler (chancellement seulement pour l'issue `hit`). Issues de `reactions.silent` : rendues,
  jamais envoyées.

### 7.8 Endurance : branchement pour T-114 sans la faire

Interface interne, seul point que T-114 remplacera :

```lua
--- Coût d'un geste défensif. T-113 : `block` passe par le compteur provisoire de garde ; `parry` et `dodge` rendent
--- toujours true (bornés par leurs délais). T-114 : retire `cost` de la jauge ; à 0, `broken = true` pour `block`, et
--- `false, 'exhausted'` pour une parade ou un pas de côté demandés (admission).
---@param src integer
---@param action 'block'|'parry'|'dodge'
---@param ctx { technique: table, weight: integer, shield: boolean, now: integer }
---@return boolean ok, boolean broken
function defense.spend(src, action, ctx) end
```

- **Coûts en données** : `stamina` de chaque technique défensive (coût d'un coup bloqué, d'une parade, d'un pas), déjà
  dans le format et contrôlés (0 à 40) ; jamais dépensés en 1.3.0.
- **Compteur provisoire** (`config.defense.guardBreak`, commenté « provisoire, remplacé par l'endurance de T-114 ») :
  un nombre de points, sans recharge continue ni affichage ni réseau ; ce n'est pas une jauge : il dit seulement « la
  garde a encaissé N coups de suite ». T-114 supprime `guardBreak` et la table `defense.points`.
- Aucune autre partie du module ne lit le compteur : T-114 change une fonction et une clé de config.

- `DeclareModifiers(list)` : pour chaque `{ key, def }`, `core.registry.add('vava_health:modifiers', key, def)` si le
  registre existe et que la clé n'y est pas ; erreur → une ligne de console ; rend le nombre déclaré.
- `OnHitAfter(fn)` : `core.hooks.after('vava_health:hit', fn)`.

État local : `guard = nil | 'asked' | 'up'`, `held` (R maintenue), dernier pas.

- **R enfoncée** (mode éveillé et actif, arme en garde, pas chancelant) : `id = techniques.pick(style, 'parade',
  attack.current(), …)` ; joué → geste `parade_epee.gesture` aussitôt (`hands.playNow`), cycle local `plan`, demande
  `use(id, 0)` dans un thread (refus : geste coupé, attente respectée, texte de `refusals`, comme `attack.lua`). `held =
  true`.
- **R maintenue** : à la fin locale de la fenêtre de parade (`closeAt`), si `held` : `pick(style, 'blocage', …)` (la
  chaîne de la parade donne `garde_epee` pendant la récupération ; sinon l'ouvreur une fois libre) → geste de garde en
  boucle (flag 49, haut du corps : on marche), `guard = 'asked'`, demande `use('garde_epee', 0)` ; réponse `true` →
  `'up'` ; refus → geste coupé, `guard = nil`.
- **R relâchée** : `held = false` ; si `guard` → geste coupé, `guard = nil`, demande `lower` (même si la réponse de la
  levée n'est pas arrivée : le serveur note `lowerRequested`) ; cycle local fermé comme au serveur (tenue minimale,
  récupération).
- **Espace** (mode actif seulement) : `pick(style, 'esquive', …)` ; direction lue **une fois** à l'appui
  (`GetControlNormal(0, 30)` et `31` : gauche, droite, avant ; rien ou arrière → geste de la technique) ; geste aussitôt
  (`defense.dodgeGestures`), demande `use(id, 0)` ; refus → geste coupé (le ped a peut-être déjà bougé : sans effet, le
  serveur n'a ouvert aucune fenêtre).
- **Attaque** pendant la garde : `attack.press` ne fait rien (`defense.guarding()`), aucun envoi.
- **Chancellement** (`attack.stagger`) et garde brisée : `defense.drop()` sans `lower` (le serveur l'a déjà fermée) ;
  il faut relâcher et ré-appuyer R pour relever la garde.

Le client ne juge ni parade, ni blocage, ni invulnérabilité : il ne montre « paré » ou « bloqué » qu'à l'arrivée de
`vava_combat:hit`.

### 8.4 Réactions (`client/reactions.lua`)

  `shakeStagger` ; tous : étincelles `effects.guarded` sur le ped du défenseur (inchangé).
- `block` : étincelles (inchangé) ; aucun tressaillement du défenseur.

## 12. Risques, et comment la spec les ferme

| Risque | Fermeture |
|---|---|
| Client qui se déclare paré, bloqué ou invulnérable | aucun RPC ne porte de résultat ; les fenêtres sont des instants **du serveur**, posés à l'acceptation ; seuls les modificateurs de la chaîne décident, sur la mémoire du serveur |
| Parade permanente, spam de R | fenêtre ≤ 500 ms (format), 200 par défaut ; parade ratée → 600 ms sans parade ; une seule place (une parade ne se superpose ni à une garde ni à un coup) ; débit 3 / s ; fenêtre utile au plus 25 % du temps en ratant tout |
| Esquive en boucle | invulnérabilité ≤ 500 ms (250 par défaut), 1,5 s entre deux départs (≤ 17 % du temps) ; `area`, `overTime`, `undodgeable` jamais évités |
| Garde éternelle (tortue) | de face seulement (120°, 160° au bouclier, tolérance + 10°) ; part arrêtée < 1 (0,40 à 0,70) ; aucune attaque garde levée (`guarding`) ; garde brisée par le compteur provisoire puis l'endurance (T-114) ; sprint coupé (client) |
| Garde ou bouclier fantômes (pile échangée, bouclier décroché) | main changée → garde annulée (hook `hold`) ; bouclier relu en mémoire (`hungOf`, numéro de pile) à chaque coup ; usure par `wear.apply` qui relit la pile |
| Défense réservée prise pour acceptée (crochet qui cède la main) | `defense.active` n'est posé qu'à l'acceptation ; les modificateurs écartent `pending`, `refused`, `cancelled` ; abaissement pendant la réservation noté (`lowerRequested`) |
| S'annuler pour sortir plus tôt d'une garde ou d'une parade | tout geste défensif est un coup au sens de T-112 : annulé, il garde son cycle (S-1) ; une garde annulée est fermée avec sa tenue minimale et sa récupération |
| Cap mensonger (client qui se tourne vers chaque attaquant) | non fermé (comme T-112 S-4, OneSync : cap déclaré par le client) ; la parade reste une affaire de **temps** tenue par le serveur, le blocage n'arrête qu'une part ; journal `vava_health_hits` (étape d'annulation, montant bloqué) pour le Conseil |
| Latence du défenseur | aucune compensation (pas de retour en arrière) : fenêtre ouverte à l'arrivée de la demande, `windup = 0` pour la parade ; le défenseur lent doit anticiper davantage (≈ un aller de son ping). Réglage T-119 : fenêtre jusqu'à 500 ms permise par le format (§ 14-6) |
| Modificateur lent ou en erreur | sortie en une lecture si personne ne se défend ; natives seulement quand une fenêtre est ouverte ; erreur : `vava_health` ignore le modificateur pour ce coup (le coup porte : aucune invulnérabilité par panne) |
| Suite manquée (erreur entre la décision et le hook `after`) | mémo bornée (`memoMax`) et purgée (`memoMs`) ; au pire la parade n'est pas marquée réussie (délai appliqué), l'attaquant ne chancelle pas : aucun gain pour un tricheur |
| Usure dans la chaîne (lenteur) | différée par `SetTimeout(0)`, hors de la chaîne ; une écriture au plus par coup défendu |
| Envoi à tous, surcharge | aucun évènement nouveau ; l'issue d'un coup défendu **remplace** son `hit` ; garde tenue : 0 octet ; `dodge` silencieux |
| Boucle par image au repos | aucune boucle ajoutée ; la garde utilise la boucle existante du mode, qui ne tourne qu'éveillée et active |
| Saut ou roulade involontaires | Espace n'agit qu'en mode combat actif ; saut (22) et recharger (45) coupés seulement dans ce mode |
| Chancellement en chaîne | chancellement forcé seulement pour l'attaquant paré (son geste) et la garde brisée (4 coups) ; immunité renouvelée à chaque fois (aucun Fendant ne refait chanceler avant 3 s) |

Ce que T-113 fixe pour ne pas les gêner :
- **Issues nommées, une par coup, dans le message déjà envoyé** `vava_combat:hit(attaquant, cible, issue)` : `hit`,
  `stagger`, `down`, `block` (même partiel), `parry`, `break` (garde brisée), `dodge`, `absorb`. L'ordre des trois valeurs
  ne change pas : T-155 **ajoute** le montant en 4e valeur (entier en dixièmes, ≈ + 2 o) sans nouveau message. Le
  montant est déjà dans le résultat de la chaîne lu par `reactions.after` (`applied`, `blocked`, `absorbed`).
- `dodge` et `absorb` sont **nommés mais silencieux** par `config.reactions.silent` : T-155 n'a qu'à retirer ces issues
  de la liste (et choisir de ne les envoyer qu'à l'attaquant et à la cible par `bridge.Send`, au lieu de `SendNear`).
- Textes à afficher (T-155) : `parry` « Paré », `block` « Bloqué » (avec le reste appliqué), `dodge` « Esquivé »,
  `absorb` « Absorbé », `break` « Garde brisée », `stagger` et `down` distingués.
- Un coup d'une autre ressource défendu n'envoie rien en 1.3.0 ; le hook `vava_combat:defended` en porte l'issue.
- **T-156** : les modificateurs ne décident que sur `defense.active[cible]`, tenu pour des **joueurs** ; un mannequin
  (pas un joueur) n'est jamais défendu, et un calcul « à blanc » de la chaîne ne déclenche aucune suite tant qu'il ne
  passe pas par `vava_health:hit` (les suites sont liées à un `hitId` réel par le hook `after`). Si T-156 veut un
  mannequin qui pare ou bloque, il posera un geste défensif d'essai dans `defense.active` sous une clé qui n'est pas un
  numéro de joueur : à spécifier par T-156.

## 14. À trancher (options et recommandation)

1. **Touches.** (a) R : appui = parade, maintenu = garde ; Espace = pas de côté (mode actif). (b) Trois touches : R garde,
   C parade, Espace pas. (c) Clic droit maintenu = garde (comme Mordhau), lourde déplacée : contraire à T-112.
   *Recommandation : (a)* — une touche défensive apprend le bon geste (on pare en levant la garde), aucune lettre de
   ZQSD (A, Q, Z prises en AZERTY), rien en commun avec la magie ni la voix (Z), le chat (T), la santé (G, E).
2. **Endurance avant T-114.** (a) Garde jamais brisée jusqu'à T-114 (coûts en données seulement). (b) Coûts en données +
   interface `defense.spend` + **compteur provisoire** de coups bloqués (4, 6 au bouclier, lourd = 2, remis à zéro après
   3 s sans coup). (c) Une jauge d'endurance minimale. *Recommandation : (b)* — testable dès T-113, sans jauge, sans HUD,
   remplacé par une fonction et une clé.
3. **Parade d'un coup non parable (Fendant).** (a) Rien : il porte. (b) Bloqué comme par une garde. *Recommandation : (a)*,
   lisible : le lourd se bloque ou s'esquive.
4. **Ce que l'on évite, bloque, pare.** Pas de côté : `melee` et `ranged` (projectiles de sorts compris), jamais `area`,
   `overTime`, `undodgeable`, `native`, `reflected`. Garde et parade : `melee` seulement. *Recommandation : retenir* ;
   bloquer un sort au bouclier : plus tard (une ligne de config, `block.tags`), à décider avec la magie.
5. **Chancellement forcé.** (a) La parade et la garde brisée ignorent l'immunité en cours et la renouvellent. (b) Elles la
   respectent (une parade sur un attaquant immunisé ne le fait pas chanceler ; issue à part). *Recommandation : (a)* :
   l'attaquant paré l'a cherché, la garde brisée est gagnée ; l'immunité renouvelée empêche toute chaîne de contrôles.
6. **Latence.** (a) Aucune compensation, `windup = 0`, réglage de la fenêtre à T-119. (b) Fenêtre allongée du ping du
   défenseur (`GetPlayerPing`, borné). (c) Retour en arrière des positions. *Recommandation : (a)* ; (b) n'aide qu'à
   l'appui trop tôt et favorise un ping gonflé ; (c) est hors de portée en v1.
7. **Esquive mains vides.** (a) Seulement arme en main (mode combat). (b) Aussi mains vides (un mage esquive).
   *Recommandation : (a) en v1* ; (b) touche la règle d'éveil du mode et `vava_magic` : à voir avec T-149 ou T-115.
8. **Usure de la défense.** Parade : l'arme du défenseur s'use (fer contre fer) ; blocage : le bouclier s'il est au bras,
   sinon l'arme ; esquive : rien. *Recommandation : retenir* (le menuisier et le forgeron vivent aussi de la défense).
9. **Sortie de garde.** (a) `garde_epee.chain = {}` : 250 ms de récupération avant toute attaque. (b) Riposte directe
   depuis la garde. *Recommandation : (a)* ; la riposte se gagne par la parade (attaquant chancelant 0,9 s).
10. **Valeurs de départ** : garde 100 / 200 / 250 ms, arc 120° (160° au bouclier) ; parade 0 / 200 / 250, arc 120°,
    600 ms après un raté ; pas de côté 50 / 250 / 350, 1,5 s entre deux ; garde brisée 1,2 s ; coûts 8 / 6 / 20.
    *Recommandation : retenir pour la porte T-119.*

## 15. Décisions à confirmer

Recommandations de cette spec (le porteur du projet a délégué : elles sont retenues sauf avis contraire) :

1. Touches : **R** (appui bref : parade ; maintenu : garde) et **Espace** (pas de côté, mode combat actif seulement ;
   saut et recharger coupés dans ce mode).
2. Endurance : coûts en données (`stamina`), interface interne `defense.spend` remplacée par T-114, **compteur
   provisoire** de garde brisée (4 coups, 6 au bouclier, un coup lourd compte 2, remis à zéro après 3 s sans coup).
3. Pas de nouveau RPC pour parer, se garder, esquiver : `vava_combat:use` les accepte ; un seul RPC nouveau,
   `vava_combat:lower`. Aucun évènement nouveau : issues `parry`, `block`, `break` dans `vava_combat:hit`.
4. Format des techniques **selon le type** : `windup` dès 0 et pas de `damage`, `parryable`, `staggers`, `hit.range` pour
   les types défensifs ; `hit.angle` = arc protégé ; esquive sans `hit`.
5. Fendant non parable : il se bloque ou s'esquive, la parade ne le retient pas.
6. Pas de côté : évite les coups `melee` et `ranged` (projectiles de sorts compris), jamais les zones, les effets qui
   durent, `undodgeable`. Garde et parade : corps à corps seulement.
7. Parade réussie et garde brisée font chanceler **même pendant l'immunité**, qu'elles renouvellent.
8. Aucune compensation de latence ; parade sans préparation (`windup = 0`) ; fenêtres réglées à T-119.
9. Pas de côté seulement arme en main en v1.
10. Usure : l'arme qui pare, le bouclier (ou l'arme) qui bloque ; rien sur une esquive.
11. Pas de riposte directe depuis la garde (`chain = {}`) ; la riposte vient de la parade.
12. Un blocage même partiel est montré « bloqué » (étincelles, pas de tressaillement), et le Fendant bloqué ne fait pas
    chanceler.
13. Valeurs de départ du § 14-10.

Retenues le 31 octobre 2026 : toutes les recommandations ci-dessus (délégation du porteur du projet).
